# 2.4 เทคโนโลยีปัญญาประดิษฐ์และสถาปัตยกรรมระบบ

## 2.4.1 สถาปัตยกรรม Retrieval-Augmented Generation

Retrieval-Augmented Generation (RAG) เป็นแนวทางที่เชื่อมการค้นคืนข้อมูลจากแหล่งความรู้เข้ากับการสร้างข้อความด้วยโมเดลภาษาขนาดใหญ่ (Large Language Model: LLM) โดยนำหลักฐานที่ค้นพบมาเป็นบริบทของคำถามก่อนให้โมเดลสร้างคำตอบ Gao และคณะ (2024) อธิบายแนวทาง RAG และองค์ประกอบที่ใช้เพิ่มความเกี่ยวข้องของคำตอบกับแหล่งความรู้ภายนอก ในบริบทการศึกษา RAG ช่วยให้ระบบอ้างอิงเอกสารประกอบการสอนที่กำหนด แทนการพึ่งพาความรู้ที่โมเดลเรียนรู้มาก่อนเพียงอย่างเดียว ทั้งนี้การค้นคืนและการอ้างอิงช่วยลดความเสี่ยงจากคำตอบที่คลาดเคลื่อน แต่ไม่สามารถรับประกันว่าจะขจัดการสร้างข้อมูลผิดพลาดได้ทั้งหมด

ไปป์ไลน์ RAG โดยทั่วไปประกอบด้วย (1) **Ingestion** รับและแปลงเอกสารให้อยู่ในรูปข้อความ (2) **Chunking** แบ่งข้อความเป็นหน่วยย่อยที่สัมพันธ์กัน (3) **Embedding** แปลงข้อความเป็นเวกเตอร์เชิงตัวเลข (4) **Vector Search** ค้นคืนชิ้นข้อความที่ใกล้เคียงกับคำถาม และ (5) **Context Building and Generation** จัดลำดับและจำกัดบริบทก่อนส่งให้ LLM สร้างคำตอบ ระบบ KMITL RAG นำเอกสารเข้า notebook และ source ใน SurrealDB บันทึกเวกเตอร์ของแต่ละชิ้นใน `source_embedding` และค้นคืนภายในขอบเขต notebook หรือ source ที่ผู้ใช้เลือกและได้รับอนุญาต

การประกอบบริบทต้องคำนึงถึงข้อจำกัดของหน้าต่างบริบท (Context Window) และจำนวนโทเคนที่โมเดลรับได้ `ContextBuilder` ในเส้นทางสนทนากับ notebook หรือ source ประเมินจำนวนโทเคนและตัดทอนเนื้อหาให้สอดคล้องกับงบประมาณที่กำหนด ขณะที่ KMITL RAG แบบถามรวดเร็วใช้ข้อจำกัดจำนวนชิ้นข้อความและจำนวนอักขระเป็นหลัก ทั้งสองวิธีมีเป้าหมายในการจำกัดข้อมูลที่จะส่งให้โมเดล แต่ถูกใช้ใน pipeline คนละส่วน

ระบบเชื่อมโมเดลผ่าน Esperanto และ model manager ซึ่งเป็นชั้นนามธรรมเหนือผู้ให้บริการ ทำให้การกำหนด credential โมเดลเริ่มต้น และการเปลี่ยน provider ทำได้โดยไม่ต้องผูก logic ของทุกฟีเจอร์กับ API รายใดรายหนึ่ง อย่างไรก็ตาม การใช้ชั้นนามธรรมไม่ได้หมายความว่าความสามารถของ provider ทุกแห่งเหมือนกัน เช่น การค้นเว็บแบบ grounding รองรับเฉพาะโมเดลที่มีเครื่องมือดังกล่าว

## 2.4.2 การประมวลผลข้อความและการตัดแบ่ง

ก่อนสร้าง embedding ระบบต้องแปลงเอกสารให้อยู่ในรูปข้อความ และแบ่งเนื้อหาให้เหมาะกับการค้นคืนและขีดจำกัดของโมเดล งานสำรวจโมเดลภาษาขนาดใหญ่ของ Zhao และคณะ (2026) เป็นบริบทประกอบการพิจารณาความสามารถและข้อจำกัดของโมเดล ส่วนการเลือกขอบเขตการแบ่งเป็นหลักการประมวลผลที่นำมาใช้ในระบบ หากแบ่งสั้นเกินไป ข้อมูลที่จำเป็นต่อความหมายอาจถูกแยกออกจากกัน แต่หากแบ่งยาวเกินไป การค้นคืนจะเจาะจงได้น้อยลงและใช้โทเคนมากขึ้น

การประมวลผลในระบบเลือก LangChain Text Splitters ตามชนิดเนื้อหา ดังนี้

| ชนิดเนื้อหา | ตัวแบ่งข้อความ | หลักการใช้งาน |
|---|---|---|
| HTML | `HTMLHeaderTextSplitter` | แบ่งตามโครงสร้างหัวข้อ HTML เช่น h1, h2 และ h3 เพื่อรักษาลำดับชั้นของเนื้อหา |
| Markdown | `MarkdownHeaderTextSplitter` | แบ่งตามหัวข้อ Markdown และคงหัวข้อไว้เพื่อรักษาบริบทของแต่ละส่วน |
| ข้อความทั่วไป | `RecursiveCharacterTextSplitter` | แบ่งตามลำดับตัวคั่นจากย่อหน้า บรรทัด ประโยค เครื่องหมายจุลภาค และช่องว่าง โดยใช้ฟังก์ชันนับโทเคนกำกับขนาด |

ค่าปริยายกำหนดขนาดชิ้นข้อความประมาณ 400 โทเคนและส่วนซ้อนทับประมาณร้อยละ 15 หรือราว 60 โทเคน การซ้อนทับช่วยรักษาข้อความที่อาจมีความหมายต่อเนื่องกันบริเวณรอยต่อ หากตัวแบ่งตามหัวข้อสร้างชิ้นที่ยาวเกินกำหนด ระบบใช้ตัวแบ่งข้อความทั่วไปแบ่งซ้ำ และกรองชิ้นว่างหรือชิ้นที่สั้นกว่าค่าต่ำสุดตามเงื่อนไข การตั้งค่าดังกล่าวช่วยให้แต่ละชิ้นมีขนาดใกล้เคียงกันโดยยังคงโครงสร้างหัวข้อของเอกสารที่รองรับ

## 2.4.3 ฐานข้อมูลเวกเตอร์และการค้นหาความคล้ายคลึง

Embedding คือการแทนข้อความด้วยเวกเตอร์ในปริภูมิตัวเลข เพื่อให้ระบบคำนวณความใกล้เคียงเชิงความหมายระหว่างคำถามกับข้อความในคลังได้ Wang และคณะ (2021) กล่าวถึงระบบจัดการข้อมูลเวกเตอร์และความสำคัญของการค้นหาเวกเตอร์ในงานประยุกต์ เมื่อฝังคำถามและชิ้นเอกสารด้วย embedding model เดียวกัน เวกเตอร์ทั้งสองมีจำนวนมิติที่สอดคล้องกันและสามารถนำมาเปรียบเทียบได้

ระบบใช้ Cosine Similarity เพื่อวัดความคล้ายคลึงจากมุมระหว่างเวกเตอร์ โดยคำนวณได้ดังนี้

$$
\operatorname{cosine}(A,B)=
\frac{A\cdot B}{\lVert A\rVert\lVert B\rVert}
=
\frac{\sum_{i=1}^{n} A_iB_i}
{\sqrt{\sum_{i=1}^{n}A_i^2}\sqrt{\sum_{i=1}^{n}B_i^2}}
$$

เมื่อ \(A\) คือเวกเตอร์ของคำถาม \(B\) คือเวกเตอร์ของชิ้นเอกสาร \(A_i\) และ \(B_i\) คือค่ามิติที่ \(i\) และ \(n\) คือจำนวนมิติของเวกเตอร์ ค่า similarity สูงหมายถึงทิศทางของเวกเตอร์ใกล้เคียงกันมากขึ้น ภายใต้เงื่อนไขว่าเวกเตอร์ไม่เป็นเวกเตอร์ศูนย์และมีมิติเท่ากัน

ตัวอย่างเพื่อแสดงการคำนวณ หาก \(A=(1,0)\), \(B_1=(0.8,0.6)\) และ \(B_2=(0,1)\) จะได้ \(\operatorname{cosine}(A,B_1)=0.8\) และ \(\operatorname{cosine}(A,B_2)=0\) จึงจัดอันดับ \(B_1\) ว่าใกล้เคียงคำถามมากกว่า ในระบบจริงเวกเตอร์มีหลายมิติตาม embedding model และ SurrealDB คำนวณ `vector::similarity::cosine` ระหว่างเวกเตอร์คำถามกับฟิลด์ embedding ของ `source_embedding`, `source_insight` หรือ `note` พร้อมตรวจว่าขนาดเวกเตอร์ตรงกันก่อนจัดอันดับผลลัพธ์

## 2.4.4 กระบวนการทำงานแบบหลายตัวแทน

การทำงานแบบหลายตัวแทน (Multi-Agent Workflow) แบ่งงานประมวลผลออกเป็นขั้นหรือบทบาทย่อยที่มีหน้าที่ชัดเจน และประสานผลลัพธ์ผ่านสถานะร่วม Xi และคณะ (2023) กล่าวถึงการใช้ตัวแทนและเครื่องมือในระบบปัญญาประดิษฐ์ LangGraph สนับสนุนการกำหนดโหนด เส้นทาง และการส่งข้อมูลระหว่างขั้นตอน จึงใช้สร้าง workflow ที่ทำงานมากกว่าการเรียกโมเดลเพียงครั้งเดียว

กราฟ Ask ของ Open Notebook แบ่งการทำงานเชิงตรรกะเป็นสามส่วน ได้แก่

1. **Strategy:** สร้างแผนและคำค้นที่จำเป็นต่อการตอบคำถาม โดยตรวจรูปแบบผลลัพธ์ให้ตรงกับ schema ของแผนค้นหา และกรองคำค้นที่ว่าง
2. **Provide Answer:** ส่งคำค้นแต่ละรายการไปค้นคืนเอกสาร จากนั้นให้โมเดลสร้างคำตอบย่อยจากหลักฐานที่พบ งานค้นหาอาจถูกกระจายออกเป็นหลายโหนดตามจำนวนคำค้น
3. **Final Answer:** รวบรวมคำตอบย่อยและสังเคราะห์เป็นคำตอบสุดท้าย หากไม่มีคำตอบที่ใช้ได้ ระบบรายงานข้อผิดพลาดแทนการสร้างผลสำเร็จปลอม

โครงสร้างนี้ใช้กับกราฟ Ask ของ Open Notebook โดยตรง ส่วน KMITL RAG แบบถามรวดเร็วใช้การค้นคืนและสร้างคำตอบใน pipeline ที่ต่างออกไป และเรียกค้นเว็บเพิ่มเติมได้ตามโหมดหรือความครอบคลุมของข้อมูล จึงไม่ควรเหมารวมว่าทุกการถามตอบในแพลตฟอร์มใช้ multi-agent graph ชุดเดียวกัน

## 2.4.5 การจัดสรรโมเดลภาษาแบบพลวัต

การจัดสรรโมเดลแบบพลวัต (Dynamic LLM Routing) เลือกโมเดลให้เหมาะกับขนาดงานและต้นทุนโดยไม่บังคับใช้โมเดลเดียวกับทุกคำขอ Chen, Zaharia และ Zou (2023) นำเสนอแนวคิด FrugalGPT เพื่อพิจารณาประสิทธิภาพและต้นทุนของการเรียกใช้ LLM ในระบบ

ในระบบนี้ `provision_langchain_model` นับจำนวนโทเคนของเนื้อหาที่จะส่งไปยังโมเดล หากมีมากกว่า 105,000 โทเคน ระบบเลือกโมเดลที่กำหนดเป็น `large_context` หากไม่เกินเกณฑ์จะเลือกโมเดลที่ระบุโดยผู้ใช้หรือโมเดลปริยายตามชนิดงาน กลไกดังกล่าวเป็นการกำหนดเส้นทางจากเกณฑ์จำนวนโทเคนและการตั้งค่าโมเดล ไม่ใช่การค้นพบหน้าต่างบริบทของโมเดลทุกตัวแบบอัตโนมัติ เกณฑ์และค่าโมเดลจึงต้องกำหนดให้เหมาะกับ provider ที่ใช้งานจริง

## 2.4.6 การควบคุมโครงสร้างผลลัพธ์ของปัญญาประดิษฐ์

ผลลัพธ์จาก LLM เป็นข้อความที่อาจไม่ตรงกับโครงสร้างที่โปรแกรมต้องการ การกำหนดรูปแบบผลลัพธ์และตรวจสอบข้อมูลจึงเป็นส่วนสำคัญของระบบที่นำผล AI ไปใช้ต่อ Beurer-Kellner และคณะ (2023) เสนอแนวคิด Prompting Is Programming ซึ่งเชื่อมการออกแบบ prompt กับการกำหนดรูปแบบข้อมูลที่นำไปประมวลผลได้

ฟีเจอร์ AI Quiz กำหนดให้โมเดลส่งผลลัพธ์เป็น JSON ที่มีคำถาม ตัวเลือก คำตอบที่ถูกต้อง และคำอธิบาย จากนั้นระบบแปลงข้อมูลเป็นโมเดล Pydantic และตรวจเงื่อนไขสำคัญ เช่น แต่ละข้อมีตัวเลือกสี่รายการ คำตอบที่ถูกต้องต้องปรากฏอยู่ในตัวเลือก และข้อมูลคำถามต้องมีรูปแบบที่รองรับก่อนบันทึกเป็นเซสชัน Quiz กระบวนการจริงจึงเป็นการกำหนดรูปแบบด้วย prompt ร่วมกับการ parse และตรวจ invariant ในแอปพลิเคชัน ไม่ใช่การรับประกันจาก JSON Schema ของ provider ทุกแห่ง

หลักการเดียวกันใช้กับ AI Roadmap ซึ่งตรวจโครงสร้างโหนดและเส้นเชื่อมให้สอดคล้องกัน ส่วนแนวคิดการสร้าง AI Flashcards อาจเป็นการประยุกต์ใช้เชิงทฤษฎีของ structured output ได้ แต่ในฟีเจอร์ที่ตรวจสอบในระบบปัจจุบันมีการสร้าง AI Quiz และ Roadmap ไม่พบ workflow สร้าง flashcards แยกต่างหาก จึงอธิบายการประยุกต์ใช้ตามฟังก์ชัน Quiz ที่มีอยู่จริง
