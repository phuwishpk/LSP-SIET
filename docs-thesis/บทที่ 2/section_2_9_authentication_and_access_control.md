# 2.9 ระบบการยืนยันตัวตนและการควบคุมสิทธิ์

## 2.9.1 การมอบสิทธิ์และการเข้าสู่ระบบด้วย Google

OAuth เป็นกรอบการมอบสิทธิ์ให้แอปพลิเคชันเข้าถึงทรัพยากรภายใต้การอนุญาตของผู้ใช้ โดยไม่จำเป็นต้องเปิดเผยรหัสผ่านของผู้ใช้แก่แอปพลิเคชันที่ร้องขอ ส่วน OpenID Connect เพิ่มชั้นการยืนยันตัวตนบน OAuth เพื่อให้ client ได้รับข้อมูลตัวตนตาม scope ที่อนุญาต แนวทาง OAuth 2.1 ที่อ้างในเอกสารต้นฉบับเป็นกรอบสำหรับพิจารณาการแลกเปลี่ยนรหัสและการป้องกันคำขอ (Hardt, Parecki, & Lodderstedt, 2026)

ระบบรองรับการเข้าสู่ระบบ Google Workspace โดย browser เริ่มกระบวนการกับ backend แล้วเปลี่ยนไปยังหน้าอนุญาตของ Google ด้วย authorization code flow และ scope `openid email profile` เมื่อ Google ส่ง authorization code กลับมายัง callback ส่วนติดต่อจะส่ง code และ state ให้ API แลกเปลี่ยนเป็นข้อมูลผู้ใช้ ระบบตรวจสอบ state ที่ลงนามและมีเวลาหมดอายุ ก่อนเรียกข้อมูลผู้ใช้จาก Google และเชื่อมบัญชีเข้ากับบทบาทใน workspace ตามโดเมนอีเมล รายชื่อผู้สอนที่อนุญาต และการกำหนดผู้ดูแล

รายละเอียดนี้อธิบายการทำงานที่ตรวจพบใน implementation ซึ่งใช้ OAuth/OIDC ของ Google และ signed state เพื่อช่วยป้องกันคำขอปลอม ไม่ควรกล่าวว่าระบบรองรับข้อกำหนด OAuth 2.1 ครบทุกประการโดยไม่มีการตรวจสอบเพิ่มเติม โดยเฉพาะการใช้ PKCE ซึ่งไม่พบการสร้าง `code_verifier` หรือ `code_challenge` ในขั้นตอนปัจจุบัน

## 2.9.2 การยืนยันตัวตนแบบไร้สถานะด้วย JSON Web Token

JSON Web Token (JWT) เป็นโทเคนที่บรรจุ claims และลงลายมือชื่อเพื่อให้ API ตรวจสอบที่มาและความถูกต้องของข้อมูลได้ โดยไม่ต้องเก็บ session object แยกสำหรับทุกคำขอ ระบบออก access token ที่ใช้ HS256 และกำหนด claims ได้แก่ subject ของผู้ใช้ `username`, issuer, audience, เวลาออกโทเคน และเวลาหมดอายุ ค่าเริ่มต้นของอายุ access token กำหนดเป็นเจ็ดวันและปรับได้ผ่านการตั้งค่าระบบ

ไคลเอนต์ส่ง JWT ใน `Authorization: Bearer` เมื่อ backend ตรวจสอบลายมือชื่อ issuer, audience และวันหมดอายุแล้ว จะใช้ subject ค้นข้อมูลบัญชีและแนบบริบทผู้ใช้เข้ากับคำขอ คำว่าไร้สถานะหมายถึงไม่ต้องเก็บ session ฝั่งเซิร์ฟเวอร์เพื่อยืนยันทุกคำขอ แต่ไม่ได้หมายความว่าไม่ต้องตรวจฐานข้อมูลเลย ระบบยังอ่านข้อมูลผู้ใช้เพื่อยืนยันบทบาทและตรวจสถานะระงับบัญชี เพื่อให้การเปลี่ยนสิทธิ์หรือการระงับบัญชีมีผลกับคำขอที่ได้รับ token ไปแล้ว

## 2.9.3 การควบคุมการเข้าถึงตามบทบาท

การควบคุมการเข้าถึงตามบทบาท (Role-Based Access Control: RBAC) กำหนดสิทธิ์ผ่านบทบาทของผู้ใช้แทนการกำหนดสิทธิ์แยกให้ผู้ใช้แต่ละราย Rahaman และคณะ (2023) ศึกษารูปแบบการออกแบบ access control ในสถาปัตยกรรม Cloud-Native ระบบแพลตฟอร์มกำหนดบทบาทหลักสามระดับ ได้แก่ ผู้ดูแลระบบ ผู้สอน และนักศึกษา และตรวจสอบคำขอที่ backend ก่อนอนุญาตให้เข้าถึง API ที่จำกัดสิทธิ์

| บทบาท | ขอบเขตการใช้งานโดยสรุป |
|---|---|
| ผู้ดูแลระบบ (Admin) | จัดการบัญชีและการตั้งค่าระดับ workspace ตรวจสอบข้อมูลและการดำเนินการของระบบ และเข้าถึงฟังก์ชันผู้ดูแล |
| ผู้สอน (Teacher) | ใช้ฟังก์ชันของผู้เรียนและเข้าถึงเครื่องมือจัดเตรียมเอกสารหรือพื้นที่วิจัยตามสิทธิ์ รวมถึงจัดการเนื้อหาในห้องที่ตนเป็นเจ้าของหรือได้รับมอบหมาย |
| นักศึกษา (Student) | ใช้ฟีด ห้องเรียน คลังส่วนบุคคล และฟีเจอร์ AI ตามขอบเขตข้อมูลและโควตาที่กำหนด |

การตรวจสอบมีทั้งระดับเส้นทาง API และระดับทรัพยากร Middleware กำหนดบทบาทขั้นต่ำที่ต้องมีสำหรับเส้นทาง เช่น การจัดการระบบสำหรับ admin และ API วิจัยบางส่วนสำหรับ teacher ขณะที่ service ตรวจสอบเพิ่มเติมว่าผู้ใช้เป็นเจ้าของห้อง สมาชิก ผู้ช่วยสอน หรือเจ้าของเซสชันที่ร้องขอหรือไม่ การตรวจระดับทรัพยากรมีความสำคัญ เพราะบทบาทเดียวกันไม่ได้ทำให้ผู้ใช้มีสิทธิ์อ่านหรือแก้ไขข้อมูลทุกห้องหรือทุกเซสชัน

ระบบยังมีสถานะบัญชี `pending` สำหรับผู้ที่ยังไม่ผ่านการอนุมัติ ซึ่งถูกจำกัดให้ใช้เฉพาะเส้นทางที่จำเป็นต่อการตรวจสอบบัญชี สถานะดังกล่าวเป็นกลไกจัดการบัญชีเพิ่มเติม ไม่ใช่หนึ่งในสามบทบาทหลักที่ใช้สรุป Actor ของระบบในแผนภาพกรณีใช้งาน
