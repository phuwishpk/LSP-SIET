# แผนการประเมินโครงงาน

## 1. วัตถุประสงค์และหลักการประเมิน

แผนนี้ใช้ประเมินวัตถุประสงค์ของโครงงานทั้ง 5 ข้อ โดยให้น้ำหนักหลักกับวัตถุประสงค์ข้อ 5:

> เพื่อประเมินประสิทธิผลของแพลตฟอร์มสนับสนุนการเรียนรู้ในการช่วยให้นักศึกษาเข้าถึงองค์ความรู้ได้อย่างเป็นระบบ สะดวก และตรงตามความต้องการ

แยกคำสำคัญในวัตถุประสงค์ออกเป็นตัวชี้วัดที่เก็บหลักฐานได้จริง ดังนี้

| ประเด็นที่ประเมิน | ความหมายในการประเมิน | หลักฐานหลัก |
|---|---|---|
| เข้าถึงได้อย่างเป็นระบบ | ผู้ใช้ค้นพบข้อมูลที่ถูกต้องจากรายวิชา/คลังที่ต้องการ และตรวจสอบที่มาของข้อมูลได้ | ผลการทำภารกิจค้นหา, Search Success Rate, ความถูกต้องของตัวกรอง, ความถูกต้องของแหล่งอ้างอิง |
| ใช้งานสะดวก | ผู้ใช้เข้าใจขั้นตอน ทำภารกิจสำเร็จได้โดยไม่สับสนหรือพึ่งผู้ช่วยมากเกินไป | Task Success Rate, จำนวนคำใบ้/ข้อผิดพลาด, คะแนน SUS และคะแนนความง่ายในการใช้งาน |
| ตรงตามความต้องการ | ข้อมูลและฟังก์ชันครอบคลุมงานเรียนที่ผู้ใช้ต้องทำ และผู้ใช้เห็นว่ามีประโยชน์ | แบบสอบถามหลังใช้งาน, คะแนนความตรงตามความต้องการ, ความเห็นปลายเปิด |

การประเมินนี้วัด **ประสิทธิผล (Effectiveness)** ว่าระบบช่วยให้ผู้ใช้บรรลุเป้าหมายการเข้าถึงองค์ความรู้ได้หรือไม่ โดยพิจารณาความสำเร็จและความถูกต้องของภารกิจเป็นหลัก ไม่ได้ตั้งประสิทธิภาพ (Efficiency)—เช่น เวลา/ทรัพยากรที่ใช้ต่อภารกิจ—เป็นผลลัพธ์ของโครงงาน มิติ “สะดวก” จะวัดจากความเข้าใจขั้นตอน การทำภารกิจได้โดยไม่สับสนหรือพึ่งผู้ช่วย และการรับรู้ความง่ายในการใช้งาน กรอบ ISO 9241-11:2018 ใช้รองรับการประเมินการใช้งาน โดยเลือกมิติที่สอดคล้องกับวัตถุประสงค์นี้ ส่วนกรอบ DeLone และ McLean ใช้สนับสนุนการพิจารณาคุณภาพระบบ คุณภาพสารสนเทศ และความพึงพอใจของผู้ใช้

**ข้อควรระวัง:** คะแนนความพึงพอใจเพียงอย่างเดียวไม่เพียงพอที่จะยืนยันว่าระบบช่วยให้เข้าถึงข้อมูลได้ดีขึ้น ต้องรายงานผลภารกิจและข้อมูลการใช้งานประกอบด้วย

## 2. การเชื่อมโยงวัตถุประสงค์กับการประเมิน

| วัตถุประสงค์ | สิ่งที่ควรประเมิน | วิธีและหลักฐาน |
|---|---|---|
| 1. ศึกษาพฤติกรรมและความต้องการของนักศึกษา | ความครอบคลุมของความต้องการและการแปลงความต้องการเป็นข้อกำหนดระบบ | สรุปผลสำรวจ/สัมภาษณ์ และตารางเชื่อมโยงความต้องการกับฟังก์ชัน |
| 2. ออกแบบและพัฒนาแพลตฟอร์มที่รวม AI และเกมมิฟิเคชัน | ฟังก์ชันทำงานตามข้อกำหนด รวมถึง RAG, Roadmap, Quiz และแต้ม | Functional Test/UAT, ผลทดสอบ AI และการตรวจจากผู้ทรงคุณวุฒิ |
| 3. ส่งเสริมการแบ่งปันเนื้อหาแบบเพื่อนช่วยเพื่อน | ผู้ใช้สร้าง/ค้น/ตอบสนองต่อเนื้อหาได้ และเห็นว่าพื้นที่ชุมชนเอื้อต่อการแบ่งปัน | ภารกิจโพสต์และมีปฏิสัมพันธ์, บันทึกการใช้งาน และแบบสอบถาม |
| 4. ทดลองใช้กับกลุ่มนำร่องและสังเกตการมีส่วนร่วม | การเข้าร่วมและการใช้ฟังก์ชันหลักระหว่างทดลอง รวมถึงพฤติกรรมการเรียนรู้ด้วยตนเองตามเครื่องมือที่เลือกใช้ | จำนวนผู้เข้าร่วม ผู้ใช้งานจริง จำนวนภารกิจ/โพสต์/การใช้ AI บันทึกการสังเกต และแบบวัดการเรียนรู้ด้วยตนเองก่อน–หลัง หากมีเครื่องมือที่ผ่านการตรวจสอบ |
| 5. ประเมินการเข้าถึงอย่างเป็นระบบ สะดวก และตรงความต้องการ | ความสำเร็จ/ความถูกต้องของการค้นหา ความเข้าใจและความง่ายในการทำภารกิจ และการรับรู้ว่าระบบตรงความต้องการ | ภารกิจทดสอบ + System logs + SUS + แบบสอบถามความต้องการและความพึงพอใจ |

ข้อ 5 เป็นผลลัพธ์หลัก ส่วนข้อ 1–4 เป็นหลักฐานประกอบว่าระบบถูกออกแบบ พัฒนา และทดลองใช้ตามจุดมุ่งหมาย ไม่ควรรวมคะแนนทุกข้อเป็นคะแนนเดียวโดยไม่แสดงผลรายด้าน

## 3. รูปแบบการเก็บข้อมูลที่แนะนำ

### 3.1 การทดสอบภารกิจจริง

ให้นักศึกษาทำภารกิจที่มีเป้าหมายและคำตอบอ้างอิงกำหนดไว้ล่วงหน้า ผู้สังเกตบันทึกผลโดยไม่ชี้นำขั้นตอน เช่น

1. ค้นหาเอกสารประกอบการเรียนที่ระบุชื่อหรือหัวข้อไว้ในรายวิชาที่กำหนด
2. ใช้คำค้นหาหรือตัวกรองเพื่อหาเนื้อหาที่ตรงกับโจทย์ แล้วเปิดรายการที่ถูกต้อง
3. ถาม KMITL RAG AI ด้วยคำถามจากเอกสารทดสอบ และตรวจว่าคำตอบมีแหล่งอ้างอิงรองรับ
4. เปิดดูหรือสร้างแผนการเรียนที่ตรงกับหัวข้อและเป้าหมายที่กำหนด
5. สร้างหรือค้นหาโพสต์สรุป/คำถามในคอมมูนิตี้ตามโจทย์

กรณีทดสอบการเข้าถึงโดยไม่มีสิทธิ์ให้ทำเป็น **การทดสอบระบบแยกต่างหาก** โดยผู้ทดสอบใช้บัญชีทดสอบ ไม่รวมในตัวหาร Task Success Rate ของผู้ใช้ปลายทาง

ก่อนทดสอบ ให้จัดทำเฉลยหรือ **Gold Standard** ของเอกสาร คำตอบ แหล่งอ้างอิง และสิทธิ์ที่ถูกต้องสำหรับแต่ละภารกิจ เพื่อให้ผู้ประเมินตัดสินความสำเร็จด้วยเกณฑ์เดียวกัน

มีชุดคำถามและเฉลยอ้างอิงตั้งต้นสำหรับ KMITL RAG AI พร้อมแบบฟอร์มเติมเฉลยเอกสารรายวิชาจริงใน [ชุดภารกิจและเฉลยอ้างอิง (Gold Standard)](./gold_standard_tasks.md) ชุดตั้งต้นนี้อ้างอิงบทที่ 3.4 ของโครงงาน จึงต้องนำเอกสารฉบับเดียวกันเข้าคลังทดสอบและตรวจ citation ที่ระบบแสดงก่อนใช้ หากต้องการประเมินการเข้าถึงความรู้รายวิชา ต้องเติมเอกสารและเฉลยของรายวิชาที่จะทดลองจริงเพิ่มเติม

หากต้องการอ้างว่าระบบช่วยให้บรรลุเป้าหมายได้ดีกว่าวิธีเดิม ให้กลุ่มเดียวกันทำภารกิจเทียบระหว่างวิธีเดิมกับแพลตฟอร์ม และสลับลำดับการทดลองระหว่างผู้เข้าร่วมเพื่อลดผลจากการเรียนรู้โจทย์ เปรียบเทียบความสำเร็จ ความถูกต้อง จำนวนคำใบ้/ข้อผิดพลาด และคะแนนการรับรู้ความสะดวก โดยไม่ใช้เวลาทำงานเป็นตัวชี้วัดหลัก หากไม่ได้เก็บข้อมูลเปรียบเทียบ ให้สรุปเฉพาะประสิทธิผลและความสะดวกที่ผู้ใช้รับรู้ ห้ามสรุปเชิงเหตุ–ผลว่าระบบ “เพิ่ม” ประสิทธิผลเมื่อเทียบกับวิธีเดิม

### 3.2 กลุ่มผู้ประเมิน

- **นักศึกษา:** กลุ่มผู้ใช้หลักสำหรับการทดสอบภารกิจ การใช้งาน และแบบสอบถาม
- **ผู้สอน:** ประเมินภารกิจของผู้สอน เช่น อัปโหลด/จัดการเอกสารรายวิชา และความเหมาะสมของแผนการเรียน
- **ผู้ทรงคุณวุฒิ:** แนะนำให้มีประมาณ 3–5 คน ครอบคลุมด้านเทคโนโลยีการศึกษา/การเรียนรู้ ด้านระบบสารสนเทศหรือ UX และด้าน AI/RAG หรือการวัดผล

จำนวนผู้เข้าร่วมจริงต้องระบุพร้อมที่มา หากสุ่มจากประชากรที่ทราบจำนวน สามารถคำนวณขนาดตัวอย่างด้วยสูตร Cochran และปรับสำหรับประชากรจำกัดได้:

```text
n0 = Z² p(1-p) / e²
n  = n0 / [1 + (n0-1)/N]
```

โดย `N` คือขนาดประชากร, `Z` คือค่าตามระดับความเชื่อมั่น, `p` คือสัดส่วนที่คาดการณ์ (ถ้าไม่ทราบมักเริ่มที่ 0.50) และ `e` คือค่าความคลาดเคลื่อนที่ยอมรับได้ การใช้สูตรนี้ต้องสอดคล้องกับวิธีสุ่มตัวอย่าง หากเป็นกลุ่มนำร่องแบบเลือกตามความสะดวก ให้รายงานข้อจำกัดและอย่าอ้างช่วงความเชื่อมั่นแทนการสุ่มแบบอาศัยความน่าจะเป็น

### 3.3 ข้อมูลที่ต้องบันทึก

- รหัสผู้เข้าร่วมแบบไม่ระบุตัวตน บทบาท และกลุ่มที่เกี่ยวข้องกับภารกิจ
- รหัสภารกิจ ผลสำเร็จ/ไม่สำเร็จ จำนวนคำใบ้ จำนวนข้อผิดพลาด และสาเหตุที่ทำไม่สำเร็จ
- คำค้น ตัวกรอง และผลลัพธ์ที่ระบบแสดง โดยไม่นำข้อมูลส่วนบุคคลที่ไม่จำเป็นมาเก็บ
- คำตอบ RAG และแหล่งอ้างอิงที่ใช้ตรวจสอบ
- แบบสอบถามหลังใช้งานและความเห็นปลายเปิด
- ความยินยอมของผู้เข้าร่วมและการจัดเก็บข้อมูลตามแนวทางจริยธรรมของสถาบัน

## 4. สูตรคำนวณตัวชี้วัด

### 4.1 อัตราความสำเร็จของภารกิจ

```text
Task Success Rate (%) =
(จำนวนภารกิจที่ทำสำเร็จโดยไม่ต้องให้ผู้สังเกตบอกคำตอบ
 ÷ จำนวนภารกิจที่มอบหมายทั้งหมด) × 100
```

นับภารกิจที่ผู้ใช้ทำไม่สำเร็จหรือยกเลิกเป็นไม่สำเร็จ ไม่ตัดออกจากตัวหาร

### 4.2 อัตราความสำเร็จในการค้นหา

```text
Search Success Rate (%) =
(จำนวนครั้งที่พบและเปิดข้อมูลเป้าหมายที่ถูกต้อง
 ÷ จำนวนภารกิจค้นหาทั้งหมด) × 100
```

กำหนด “พบข้อมูลถูกต้อง” ในคู่มือทดสอบล่วงหน้า เช่น ต้องเป็นเอกสารที่ตรงกับโจทย์ อยู่ในรายวิชาหรือคลังที่กำหนด และผู้ใช้มีสิทธิ์เข้าถึง

### 4.3 ความแม่นยำของผลค้นคืน (กรณีมีชุดเฉลย)

```text
Precision@k = จำนวนเอกสารที่เกี่ยวข้องในผลลัพธ์ k รายการ ÷ k
Recall@k    = จำนวนเอกสารที่เกี่ยวข้องซึ่งค้นพบ ÷ จำนวนเอกสารที่เกี่ยวข้องทั้งหมดในชุดเฉลย
```

ใช้เมื่อมีผู้ทรงคุณวุฒิหรือผู้จัดทำกำหนดรายการเอกสารที่เกี่ยวข้องไว้เป็นชุดเฉลยก่อนทดสอบ มิฉะนั้นให้ใช้ Search Success Rate และรายงานวิธีตัดสินผลแทน

### 4.4 คะแนนแบบสอบถามมาตราส่วน 5 ระดับ

กำหนดคะแนน 1 = ไม่เห็นด้วยอย่างยิ่ง ถึง 5 = เห็นด้วยอย่างยิ่ง

```text
ค่าเฉลี่ยรายข้อ/รายด้าน = Σคะแนนของผู้ตอบ ÷ จำนวนคำตอบที่ใช้คำนวณ
ร้อยละผู้เห็นด้วย = [(จำนวนผู้ตอบระดับ 4 และ 5) ÷ จำนวนผู้ตอบทั้งหมด] × 100
```

คำนวณผลแยกตามสามมิติ ไม่รวมเป็นคะแนนเดียว: ด้านเป็นระบบใช้ข้อ A1–A4, ด้านสะดวกใช้ข้อ B1–B5, และด้านตรงตามความต้องการใช้ข้อ C1–C6 ในแบบสอบถาม ส่วนข้อ C7 ใช้รายงานการรับรู้ภาพรวมเท่านั้น ไม่นำไปรวมซ้ำในคะแนนรายมิติ หากไม่ได้ใช้ฟังก์ชันใด ให้ไม่นำคำตอบ “ไม่ได้ใช้งาน/ประเมินไม่ได้” มาคำนวณ

เกณฑ์เบื้องต้นจากเอกสารเกณฑ์ประเมินของโครงงานคือ ค่าเฉลี่ยอย่างน้อย 4.00 จาก 5.00 และผู้ใช้ไม่น้อยกว่าร้อยละ 80 เลือกระดับ 4 หรือ 5 ในคำถามหลัก เกณฑ์เดิมวัดคำถามภาพรวม; การนำเกณฑ์เดียวกันมาใช้พิจารณาคะแนนแยกทั้งสามมิติเป็น **ข้อเสนอให้ที่ปรึกษา/ผู้ทรงคุณวุฒิอนุมัติก่อนเก็บข้อมูล** ควรรายงานจำนวนผู้ตอบและการกระจายคะแนนด้วย ไม่รายงานค่าเฉลี่ยเพียงอย่างเดียว

### 4.5 คะแนน System Usability Scale (SUS)

ใช้แบบประเมิน SUS ฉบับภาษาไทยที่ผ่านการตรวจสอบ หรือแปลและตรวจสอบภาษาอย่างเป็นระบบ โดยไม่เปลี่ยนโครงสร้างคำถามและวิธีคิดคะแนน

```text
สำหรับข้อเลขคี่: คะแนนที่ใช้ = คะแนนตอบ − 1
สำหรับข้อเลขคู่: คะแนนที่ใช้ = 5 − คะแนนตอบ
SUS = ผลรวมคะแนนที่ปรับแล้วทั้ง 10 ข้อ × 2.5
```

คะแนนอยู่ในช่วง 0–100 เกณฑ์โครงการที่เสนอไว้เดิมคือ SUS อย่างน้อย 70 คะแนน ให้ใช้เป็นเกณฑ์ผ่านของโครงการเมื่ออาจารย์ที่ปรึกษา/คณะกรรมการเห็นชอบ ไม่ตีความคะแนน SUS เป็นร้อยละหรือคะแนนผลสัมฤทธิ์

### 4.6 คุณภาพคำตอบและแหล่งอ้างอิงของ KMITL RAG AI

ใช้ชุดคำถามทดสอบที่มีคำตอบอ้างอิงจากเอกสารที่อนุญาตให้ค้น และให้ผู้ประเมินตรวจคำตอบกับแหล่งต้นทาง

```text
อัตราคำตอบถูกต้อง (%) =
(จำนวนคำตอบที่ผู้ประเมินเห็นว่าถูกต้องและมีหลักฐานรองรับ
 ÷ จำนวนคำถามทดสอบทั้งหมด) × 100

อัตราคำตอบที่มีข้อความไร้หลักฐาน (%) =
(จำนวนคำตอบที่มีข้อกล่าวอ้างสำคัญซึ่งไม่รองรับด้วยแหล่งข้อมูล
 ÷ จำนวนคำตอบทั้งหมด) × 100

ความถูกต้องของการอ้างอิง (%) =
(จำนวนแหล่งอ้างอิงที่รองรับข้อความคำตอบ
 ÷ จำนวนแหล่งอ้างอิงที่ตรวจทั้งหมด) × 100
```

เอกสารเกณฑ์ประเมินเดิมกำหนดเป้าหมายร่างสำหรับ RAG คือคำตอบถูกต้องอย่างน้อย 80% และข้อความไร้หลักฐานไม่เกิน 5% ให้รายงานความถูกต้องของแหล่งอ้างอิงแยกต่างหาก และให้ผู้ทรงคุณวุฒิตรวจชุดคำถาม/คำตอบอ้างอิงก่อนใช้

### 4.7 ความตรงเชิงเนื้อหาของแบบสอบถามด้วย IOC

```text
IOC ของข้อคำถาม j = ΣRᵢⱼ ÷ N
```

โดย `Rᵢⱼ` คือคะแนนจากผู้ทรงคุณวุฒิคนที่ `i` ต่อข้อ `j` (`+1` = สอดคล้องกับวัตถุประสงค์, `0` = ไม่แน่ใจ, `−1` = ไม่สอดคล้อง) และ `N` คือจำนวนผู้ทรงคุณวุฒิ เกณฑ์ร่างที่ใช้คือ IOC ตั้งแต่ 0.50 ขึ้นไป; ต่ำกว่าเกณฑ์ให้แก้ไขหรือตัดข้อคำถาม พร้อมบันทึกเหตุผล เกณฑ์ดังกล่าวเป็นแนวปฏิบัติที่เสนอ ไม่ใช่ข้อบังคับสากล ต้องให้ที่ปรึกษาอนุมัติก่อนใช้

### 4.8 ความเชื่อมั่นของแบบสอบถาม

```text
Cronbach’s alpha = [k ÷ (k−1)] × [1 − (Σความแปรปรวนรายข้อ ÷ ความแปรปรวนคะแนนรวม)]
```

คำนวณแยกตามด้านที่ต้องการวัด (เช่น ความสะดวก หรือความตรงตามความต้องการ) ไม่รวมข้อคำถามต่างมิติเป็นค่าเดียวโดยไม่มีเหตุผล ค่า alpha อย่างน้อย 0.70 ใช้เป็นเกณฑ์เบื้องต้นสำหรับเครื่องมือที่อยู่ระหว่างพัฒนา แต่ไม่ใช่หลักฐานยืนยันความตรงของเครื่องมือ และควรพิจารณาความสัมพันธ์รายข้อกับคะแนนรวมร่วมด้วย

### 4.9 อัตราผ่านการทดสอบระบบและการมีส่วนร่วม

```text
Functional Test Pass Rate (%) =
(จำนวนกรณีทดสอบที่ได้ผลตรงตามที่คาดหวัง ÷ จำนวนกรณีทดสอบทั้งหมด) × 100

อัตราการมีส่วนร่วมในคอมมูนิตี้ (%) =
(จำนวนผู้ใช้ที่ใช้งานจริงและทำกิจกรรมที่กำหนดอย่างน้อย 1 ครั้ง
 ÷ จำนวนผู้ใช้ที่ใช้งานจริงทั้งหมด) × 100
```

นับกรณีทดสอบสิทธิ์และบัญชีแต้มแยกตามเงื่อนไขสำคัญ โดยการเข้าถึงข้อมูลข้ามสิทธิ์ที่สำเร็จแม้เพียงหนึ่งกรณีต้องรายงานเป็นข้อบกพร่อง ไม่เฉลี่ยกลบกับกรณีอื่น

## 5. เกณฑ์ผ่านเบื้องต้นของโครงงาน

ค่าในตารางเป็นเกณฑ์ที่ปรากฏในเอกสาร “การตั้งสมมติฐานและการกำหนดเกณฑ์ประเมิน” ของโครงงาน และจัดกลุ่มใหม่ให้ตรวจสอบได้ เกณฑ์เหล่านี้เป็น **ข้อเสนอสำหรับให้ที่ปรึกษาและผู้ทรงคุณวุฒิพิจารณาก่อนเก็บข้อมูลจริง** ไม่ใช่ผลการประเมินที่เกิดขึ้นแล้ว

ให้ตัดสินวัตถุประสงค์ข้อ 5 แยกตามสามมิติหลัก ไม่เฉลี่ยรวมกันจนปิดบังจุดอ่อน:

1. **เป็นระบบ:** ผ่านเมื่อผู้ใช้ค้นพบข้อมูลที่ถูกต้องและได้รับอนุญาตตามภารกิจ โดยรายงาน Task Success Rate, Search Success Rate, ความถูกต้องของตัวกรอง และการตรวจสอบแหล่งอ้างอิง
2. **สะดวก:** ผ่านเมื่อผู้ใช้ทำภารกิจสำเร็จโดยไม่สับสนหรือพึ่งคำใบ้มากเกินไป และคะแนน SUS/คะแนนความง่ายผ่านเกณฑ์ โดยไม่ใช้เวลาเป็นตัวตัดสินประสิทธิผล
3. **ตรงตามความต้องการ:** ผ่านเมื่อแบบสอบถามแสดงว่าผู้ใช้เห็นว่าข้อมูลและฟังก์ชันตรงกับงานเรียนตามเกณฑ์ที่กำหนด พร้อมความเห็นปลายเปิดประกอบ

หากตัวชี้วัดมิติใดไม่ผ่าน ให้รายงานมิตินั้นว่า “ยังไม่ผ่านเกณฑ์” และอธิบายสาเหตุ ไม่สรุปจากคะแนนเฉลี่ยรวมเพียงค่าเดียว

## 6. การตรวจสอบโดยผู้ทรงคุณวุฒิและการทดลองนำร่อง

1. จัดทำตารางเชื่อมโยงวัตถุประสงค์ → มิติประเมิน → ข้อคำถาม/ภารกิจ → สูตร → เกณฑ์ผ่าน
2. ให้ผู้ทรงคุณวุฒิ 3–5 คนตรวจความสอดคล้อง ความชัดเจน ความครอบคลุม และความเป็นไปได้ในการทำภารกิจ โดยคำนวณ IOC สำหรับข้อคำถามที่ใช้วัดวัตถุประสงค์
3. แก้ข้อคำถามหรือภารกิจที่ IOC ต่ำกว่าเกณฑ์ และบันทึกทั้งคะแนนและข้อเสนอแนะ
4. ทดลองใช้แบบสอบถามและภารกิจกับกลุ่มเล็กก่อนเก็บข้อมูลจริง เพื่อตรวจความชัดเจนของภาษาและคำสั่ง รวมถึงความเป็นไปได้ในการทำภารกิจ
5. คำนวณ Cronbach’s alpha แยกตามมิติของแบบสอบถามที่มีหลายข้อ หากค่าต่ำให้ตรวจข้อคำถามและปรับเครื่องมือก่อนเก็บจริง
6. กำหนดชุดคำถาม RAG และคำตอบอ้างอิงร่วมกับผู้เชี่ยวชาญ พร้อมระบุวิธีตัดสิน “ถูกต้อง”, “เกี่ยวข้อง” และ “มีหลักฐานรองรับ” ล่วงหน้า
7. เก็บแบบฟอร์มฉบับตรวจแล้ว ผล IOC รุ่นที่แก้ไข รายงานการทดลองนำร่อง และข้อมูลทดสอบไว้เป็นหลักฐานให้คณะกรรมการตรวจสอบย้อนกลับ

## 7. ข้อจำกัดในการแปลผล

- ผลจากกลุ่มนำร่องใช้สะท้อนการใช้งานในบริบทและกลุ่มตัวอย่างที่ศึกษา ไม่ควรสรุปแทนนักศึกษาทุกหลักสูตรหากไม่ได้สุ่มตัวอย่างให้รองรับ
- คะแนนแบบสอบถามเป็นการรับรู้ของผู้ใช้ ต้องรายงานควบคู่กับผลภารกิจและบันทึกระบบ
- การอ้างว่าระบบทำให้ “ผลสัมฤทธิ์ทางการเรียนเพิ่มขึ้น” ต้องมีการทดสอบผลการเรียนก่อน–หลังหรือกลุ่มเปรียบเทียบโดยตรง ซึ่งอยู่นอกตัวชี้วัดหลักของวัตถุประสงค์ข้อ 5
- เกณฑ์ผ่านทั้งหมดต้องได้รับการเห็นชอบจากอาจารย์ที่ปรึกษา/คณะกรรมการก่อนเริ่มเก็บข้อมูล ไม่ปรับเกณฑ์ย้อนหลังเพื่อให้ผลผ่าน
