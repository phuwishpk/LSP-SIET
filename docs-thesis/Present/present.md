# บทพูดอธิบายแผนภาพการทำงานสำหรับนำเสนอกรรมการ

เอกสารนี้เป็นแนวทางสำหรับพูดประกอบแผนภาพทั้ง 6 สไลด์ ใช้ภาษาพูดที่เข้าใจง่ายและไล่ตามลำดับการทำงานในภาพ ผู้พูดไม่จำเป็นต้องอ่านทุกคำตามต้นฉบับ สามารถย่อหรือขยายตามเวลานำเสนอได้

## วิธีอ่านสัญลักษณ์ในแผนภาพ

- **วงรี** หมายถึงจุดเริ่มต้นหรือจุดสิ้นสุดของกระบวนการ
- **สี่เหลี่ยม** หมายถึงขั้นตอนที่ระบบหรือผู้ใช้กำลังทำ
- **ข้าวหลามตัด** หมายถึงจุดตรวจสอบหรือตัดสินใจ ซึ่งอาจแยกเป็นทางผ่านและไม่ผ่าน
- **สี่เหลี่ยมด้านขนาน** หมายถึงข้อมูลที่ผู้ใช้ส่งเข้ามาหรือผลลัพธ์ที่ระบบส่งกลับ
- **ทรงกระบอก** หมายถึงข้อมูลที่ถูกบันทึกหรืออ่านจากฐานข้อมูล
- **ลูกศร** แสดงลำดับและทิศทางการทำงาน

หากแผนภาพมีหลายทางแยก ให้ชี้ที่สัญลักษณ์เงื่อนไขก่อน แล้วอธิบายทีละทางว่าเมื่อผ่านระบบทำอะไรต่อ และเมื่อไม่ผ่านระบบแจ้งอะไรหรือจบกระบวนการอย่างไร

## สไลด์ที่ 1: ระบบคอมมูนิตี้และกระบวนการเผยแพร่เนื้อหา

**หัวข้อที่เกี่ยวข้อง:** บทที่ 3 หัวข้อ 3.3.3.1  
**แผนภาพที่เกี่ยวข้อง:** รูปที่ 3.8 การเผยแพร่เนื้อหาและบันทึกแต้ม

### ใจความสำคัญ

แผนภาพนี้อธิบายตั้งแต่ผู้ใช้ส่งโพสต์เข้าระบบ การตรวจข้อมูลและสิทธิ์ การบันทึกโพสต์ ไปจนถึงการตรวจว่าโพสต์นั้นได้รับแต้มตามกติกาหรือไม่ จุดสำคัญคือ **การโพสต์สำเร็จและการได้รับแต้มเป็นคนละเงื่อนไขกัน** ผู้ใช้อาจเผยแพร่โพสต์ได้สำเร็จ แต่ไม่ได้แต้ม หากกิจกรรมนั้นไม่เข้าเกณฑ์หรือได้รับแต้มครบเพดานแล้ว

### บทพูดสำหรับนำเสนอ

“สไลด์นี้แสดงขั้นตอนการเผยแพร่เนื้อหาในระบบคอมมูนิตี้ และการเชื่อมต่อกับระบบแต้มครับ/ค่ะ

เริ่มจากผู้ใช้เขียนโพสต์ อาจเป็นคำถาม สรุปเนื้อหา หรือเนื้อหาประเภทอื่น พร้อมแนบไฟล์ได้ถ้าต้องการ จากนั้น Client ซึ่งก็คือส่วนที่ผู้ใช้กำลังใช้งาน จะส่งข้อมูลโพสต์ ไฟล์แนบ และข้อมูลยืนยันตัวตนที่เรียกว่า JWT ไปยัง API

เมื่อ API ได้รับคำขอ ระบบจะตรวจสอบข้อมูลหลายส่วนก่อนบันทึก ได้แก่ ตรวจว่า JWT ถูกต้องหรือไม่ ตรวจบทบาทของผู้ใช้และสิทธิ์ในห้อง ตรวจว่าข้อมูลโพสต์ครบและถูกต้องหรือไม่ ตรวจไฟล์แนบ และตรวจว่ามีโพสต์ซ้ำหรือไม่ การตรวจเหล่านี้ช่วยป้องกันผู้ไม่มีสิทธิ์ส่งเนื้อหา ป้องกันไฟล์ที่ไม่ผ่านข้อกำหนด และลดการส่งโพสต์เดิมซ้ำ

ถ้าข้อมูลหรือสิทธิ์ไม่ผ่าน ระบบจะแจ้งข้อผิดพลาดกลับไปยัง Client และจบกระบวนการ โดยยังไม่บันทึกโพสต์ แต่ถ้าผ่าน ระบบจะบันทึกโพสต์และจัดการไฟล์แนบ โดยข้อมูลโพสต์หลักถูกเก็บใน MariaDB

หลังจากบันทึกโพสต์แล้ว ระบบ Point Service จะตรวจต่อว่ากิจกรรมนี้ได้รับแต้มได้หรือไม่ โดยดูชนิดของกิจกรรม ความครบถ้วน ประวัติการได้รับแต้มซ้ำ และเพดานที่กำหนดไว้ ถ้าไม่เข้าเกณฑ์ โพสต์ยังเผยแพร่สำเร็จ เพียงแต่ไม่มีการให้แต้มในครั้งนั้น

แต่ถ้ากิจกรรมเข้าเกณฑ์ ระบบจะปรับยอดแต้มและเพิ่มประวัติรายการแต้มภายในธุรกรรมฐานข้อมูล พร้อมบันทึกการแจ้งเตือนที่เกี่ยวข้อง เมื่อบันทึกครบแล้วจึงยืนยันธุรกรรมและส่งผลกลับไปยัง Client ว่าโพสต์สำเร็จและได้แต้มเท่าไร

สรุปคือ ระบบตรวจสิทธิ์และความถูกต้องก่อนเผยแพร่ และแยกการตัดสินใจเรื่องแต้มออกจากการตัดสินใจเรื่องโพสต์ เพื่อให้การแบ่งปันความรู้ทำได้อย่างปลอดภัยและการให้แต้มเป็นไปตามกติกาครับ/ค่ะ”

### จุดที่ควรชี้บนภาพ

1. ชี้จุดเริ่มและข้อมูลที่ Client ส่งเข้ามา
2. ชี้ขั้นตรวจข้อมูลและสิทธิ์ แล้วอธิบายว่าทางไม่ผ่านจะแจ้งข้อผิดพลาด
3. ชี้จุดบันทึกโพสต์ใน MariaDB
4. ชี้ Point Service และเงื่อนไขการให้แต้ม
5. เปรียบเทียบสองทาง: โพสต์สำเร็จแต่ไม่ได้แต้ม กับโพสต์สำเร็จพร้อมบันทึกแต้ม
6. ปิดท้ายที่การแจ้งผลกลับไปยัง Client

### ประเด็นที่ควรจำ

- **JWT** คือข้อมูลที่ใช้ยืนยันตัวตนของผู้ใช้ในคำขอ
- **Point Service** คือส่วนที่ตรวจและคำนวณการให้แต้ม
- การไม่ผ่านเงื่อนไขแต้มไม่ได้แปลว่าโพสต์ไม่สำเร็จ
- ยอดแต้มและประวัติธุรกรรมต้องบันทึกให้สอดคล้องกัน

## สไลด์ที่ 2: ระบบแต้มและวงจร Earn-and-Burn

**หัวข้อที่เกี่ยวข้อง:** บทที่ 3 หัวข้อ 3.3.1.2  
**แผนภาพที่เกี่ยวข้อง:** รูปที่ 3.7 วงจร Earn-and-Burn Loop

### ใจความสำคัญ

แผนภาพนี้แสดงภาพรวมของการ **ได้รับแต้ม (Earn)** จากการมีส่วนร่วมที่เข้าเกณฑ์ และการ **ใช้แต้ม (Burn)** เพื่อเรียกบริการ AI แต้มเป็นหน่วยภายในระบบ ไม่ใช่เงินและไม่ใช่คะแนนผลการเรียน ทุกครั้งที่ให้ หัก หรือคืนแต้ม ระบบเก็บประวัติรายการไว้ตรวจสอบได้

### บทพูดสำหรับนำเสนอ

“แผนภาพนี้อธิบายวงจรการได้รับและการใช้แต้ม หรือ Earn-and-Burn ครับ/ค่ะ

ฝั่งแรกคือ Earn หรือการได้รับแต้ม ตัวอย่างกิจกรรม ได้แก่ โบนัสเริ่มต้น การเผยแพร่เนื้อหาที่ผ่านเงื่อนไข การได้รับการตอบสนองจากผู้ใช้อื่น หรือการทำแบบทดสอบที่มีการแชร์ ระบบจะตรวจสอบก่อนว่าผู้ใช้มีสิทธิ์ได้รับแต้ม กิจกรรมไม่ซ้ำ และยังไม่เกินเพดานรายวันที่กำหนดหรือไม่

ถ้ากิจกรรมไม่เข้าเกณฑ์ ระบบจะไม่ให้แต้มและแจ้งผล แต่ถ้าผ่าน ระบบจะบันทึกรายการ Earn และปรับยอดคงเหลือในธุรกรรมฐานข้อมูลเดียวกัน โดยยอดปัจจุบันเก็บในบัญชีแต้มของผู้ใช้ ส่วนประวัติการเปลี่ยนแปลงเก็บเป็นรายการธุรกรรม ทำให้ตรวจสอบย้อนหลังได้ว่าแต้มเพิ่มหรือลดจากเหตุการณ์ใด

หลังจากนั้นผู้ใช้สามารถเลือกใช้บริการ AI ได้ เช่น ถามตอบด้วย RAG สร้าง Quiz สร้างหรือขยาย Roadmap หรือใช้บริการอื่นที่กำหนด ระบบจะตรวจสอบบทบาทก่อน ผู้สอนหรือผู้ดูแลระบบที่อยู่ในกลุ่มยกเว้นจะไม่ถูกหักแต้มตามนโยบาย ส่วนผู้ใช้ทั่วไปต้องมีแต้มเพียงพอกับบริการนั้น

ถ้าแต้มไม่พอ ระบบจะแจ้งให้ทราบและไม่เริ่มบริการ แต่ถ้าแต้มเพียงพอ ระบบจะบันทึกรายการ Burn และปรับยอดก่อนเริ่มประมวลผลบริการ AI

จากนั้นมีจุดตรวจว่าบริการ AI ทำงานสำเร็จหรือไม่ ถ้าสำเร็จก็ส่งผลกลับให้ผู้ใช้ แต่ถ้าล้มเหลว ระบบจะตรวจต่อว่ามีการหักแต้มไปแล้วหรือยัง ถ้าหักไปแล้ว ระบบจะเพิ่มรายการคืนแต้มโดยอ้างอิงธุรกรรมเดิม และปรับยอดกลับให้ผู้ใช้ ถ้ายังไม่มีการหักแต้ม ก็แจ้งความล้มเหลวโดยไม่ต้องคืนแต้ม

ดังนั้น จุดประสงค์ของวงจรนี้คือสนับสนุนให้ผู้ใช้ร่วมสร้างความรู้ และนำแต้มไปใช้กับบริการ AI อย่างมีเงื่อนไข พร้อมมีประวัติการให้ หัก และคืนแต้มที่ตรวจสอบได้ แต้มนี้ไม่ได้ใช้แทนเงินหรือผลการเรียนครับ/ค่ะ”

### จุดที่ควรชี้บนภาพ

1. ชี้ฝั่ง Earn: กิจกรรมที่อาจทำให้ได้รับแต้ม
2. ชี้เงื่อนไขสิทธิ์ การป้องกันรายการซ้ำ และเพดาน
3. ชี้จุดบันทึกยอดปัจจุบันและประวัติธุรกรรม
4. ชี้ฝั่ง Burn: การเลือกบริการ AI และตรวจแต้มก่อนเริ่ม
5. ชี้ข้อยกเว้นตามบทบาท
6. ชี้ทางเมื่อบริการสำเร็จและเมื่อบริการล้มเหลว รวมถึงการคืนแต้ม

### ประเด็นที่ควรจำ

- Earn คือได้รับแต้มจากกิจกรรมที่เข้าเกณฑ์ ไม่ใช่ทุกการคลิก
- Burn คือใช้แต้มกับบริการที่กำหนด
- ยอดแต้มปัจจุบันกับประวัติธุรกรรมเป็นข้อมูลคนละส่วน แต่ต้องอัปเดตให้สัมพันธ์กัน
- ถ้าหักแต้มแล้วบริการล้มเหลว ระบบบันทึกรายการคืน ไม่ลบประวัติการหักเดิม

## สไลด์ที่ 3: การนำเข้าเอกสารและการสร้างคลังความรู้

**หัวข้อที่เกี่ยวข้อง:** บทที่ 3 หัวข้อ 3.4.1.1  
**แผนภาพที่เกี่ยวข้อง:** รูปที่ 3.9 Ingestion Pipeline

### ใจความสำคัญ

แผนภาพนี้อธิบายวิธีนำไฟล์ URL หรือข้อความเข้าเป็นแหล่งความรู้ ระบบตรวจสิทธิ์และบันทึกสถานะก่อนประมวลผล จากนั้นสกัดและแบ่งเนื้อหา สร้าง Embedding และจัดเก็บเพื่อให้ระบบค้นคืนได้ภายหลัง

### บทพูดสำหรับนำเสนอ

“สไลด์นี้แสดงกระบวนการนำเข้าเอกสารเพื่อเตรียมเป็นคลังความรู้ให้ระบบค้นหาและตอบคำถามครับ/ค่ะ

ผู้ใช้เริ่มจากเลือกข้อมูลที่จะนำเข้า ซึ่งอาจเป็นไฟล์ URL หรือข้อความ และเลือกว่าจะเก็บไว้ในคลังส่วนตัวหรือคลังรายวิชา จากนั้น API ตรวจสอบตัวตนและสิทธิ์ของผู้ใช้ในคลังที่เลือก ถ้าไม่มีสิทธิ์ ระบบแจ้งข้อผิดพลาดและหยุดก่อนประมวลผล เพื่อไม่ให้ข้อมูลถูกนำเข้าไปยังคลังที่ผู้ใช้ไม่ได้รับอนุญาต

ถ้าผ่านการตรวจสอบ ระบบจะบันทึกข้อมูลกำกับของเอกสารลง MariaDB และกำหนดสถานะเป็นกำลังประมวลผล หรือ processing ไว้ก่อน วิธีนี้ทำให้ผู้ใช้และผู้ดูแลติดตามได้ว่าเอกสารกำลังอยู่ในขั้นตอนไหน

ต่อมาระบบคำนวณ Content Hash เพื่อช่วยตรวจว่าเป็นเนื้อหาซ้ำหรือไม่ แล้วสกัดข้อความตามชนิดของข้อมูล เช่น อ่านข้อความจากไฟล์หรือดึงเนื้อหาจาก URL ถ้าสกัดไม่สำเร็จ ระบบจะบันทึกสถานะ failed พร้อมรายละเอียดข้อผิดพลาด แทนการรายงานว่านำเข้าสำเร็จ

เมื่อสกัดข้อความได้ ระบบสร้าง source ใน SurrealDB และเชื่อม source นั้นกับ notebook ที่เลือก จากนั้นแบ่งเนื้อหาเป็นส่วนย่อยหรือ chunks โดยพยายามแบ่งตามโครงสร้างและความหมายของเนื้อหา ค่าเริ่มต้นในเอกสารกำหนดประมาณ 400 โทเคนต่อชิ้น มีส่วนทับซ้อนประมาณ 15 เปอร์เซ็นต์ เพื่อช่วยรักษาความต่อเนื่องของประโยคหรือแนวคิดบริเวณรอยต่อ

หลังแบ่งข้อความ ระบบสร้าง Embedding ให้แต่ละ chunk Embedding คือการแปลงข้อความให้อยู่ในรูปแบบตัวเลขที่ระบบนำไปเปรียบเทียบความหมายได้ แล้วจัดเก็บทั้งข้อความย่อยและเวกเตอร์ไว้ใน SurrealDB

เมื่อสร้างและบันทึกเวกเตอร์สำเร็จ ระบบจะบันทึกจำนวน chunks จำนวนอักขระ และเปลี่ยนสถานะเอกสารเป็น ready ใน MariaDB หากขั้นตอนสร้างหรือบันทึก Embedding ล้มเหลว ระบบจะเปลี่ยนเป็น failed และเก็บข้อมูลข้อผิดพลาดไว้ให้ตรวจสอบ

สรุปคือ ก่อนนำเอกสารไปใช้ตอบคำถาม ระบบต้องตรวจสิทธิ์ สกัดเนื้อหา แบ่งข้อความ และจัดทำเวกเตอร์ให้เสร็จก่อน จึงจะค้นคืนเนื้อหาได้ครับ/ค่ะ”

### จุดที่ควรชี้บนภาพ

1. ชี้ข้อมูลนำเข้าและการเลือกคลัง
2. ชี้การตรวจสิทธิ์และการบันทึกสถานะ processing
3. ชี้การตรวจซ้ำและการสกัดเนื้อหา
4. ชี้การแบ่ง chunks และสร้าง Embedding
5. ชี้ที่จัดเก็บ source/เวกเตอร์ใน SurrealDB
6. ชี้ผลลัพธ์ ready และเส้นทาง failed

### ประเด็นที่ควรจำ

- MariaDB ใช้เก็บข้อมูลกำกับและสถานะเอกสาร ส่วน SurrealDB ใช้เก็บ source และข้อมูลเวกเตอร์ตามการออกแบบของระบบ
- Content Hash ใช้ช่วยตรวจเนื้อหาซ้ำ ไม่ใช่ขั้นตอนสร้างเวกเตอร์
- สถานะ processing, ready และ failed ช่วยให้ติดตามผลการนำเข้าได้
- การสร้าง Embedding เป็นการเตรียมข้อมูลเพื่อค้นหาตามความหมาย ไม่ใช่การเขียนคำตอบให้ผู้ใช้

## สไลด์ที่ 4: การค้นคืนและสร้างคำตอบด้วย KMITL RAG AI

**หัวข้อที่เกี่ยวข้อง:** บทที่ 3 หัวข้อ 3.4.3.1  
**แผนภาพที่เกี่ยวข้อง:** รูปที่ 3.11 Flowchart การถามตอบ KMITL RAG AI

### ใจความสำคัญ

แผนภาพนี้อธิบายวงจรถามตอบของ RAG ตั้งแต่ผู้ใช้ส่งคำถาม ตรวจตัวตนและสิทธิ์ ตรวจรูปแบบบริการและโควตา ค้นเนื้อหาที่เกี่ยวข้องจากแหล่งที่อนุญาต ส่งบริบทให้แบบจำลองสร้างคำตอบ แล้วส่งคำตอบพร้อมแหล่งอ้างอิงกลับไป

### บทพูดสำหรับนำเสนอ

“สไลด์นี้แสดงกระบวนการที่ KMITL RAG AI ใช้ตอบคำถามโดยอาศัยเอกสารในคลังความรู้ครับ/ค่ะ

เริ่มจาก Client ส่งคำถาม พร้อมระบุรูปแบบบริการและขอบเขตคลังความรู้ที่ต้องการใช้ เช่น ถามเป็นครั้งเดียว หรือใช้เซสชันที่มีโควตาหลายข้อความ รวมถึงส่ง JWT เพื่อยืนยันตัวตน

RAG API ตรวจสอบว่าคำขอมีข้อมูลครบหรือไม่ JWT ถูกต้องหรือไม่ บัญชียังใช้งานได้หรือไม่ และผู้ใช้มีสิทธิ์เข้าถึงคลังหรือห้องที่เลือกหรือไม่ ถ้าไม่ผ่าน ระบบแจ้งข้อผิดพลาดและหยุดก่อนค้นข้อมูล

ถ้าผ่าน ระบบจะกำหนด notebook หรือ source ที่ผู้ใช้เข้าถึงได้ แล้วตรวจรูปแบบบริการเพื่อคำนวณค่าใช้จ่ายตามกติกา ตัวอย่างตามค่าเริ่มต้นในเอกสารคือ การเริ่มเซสชันใหม่หัก 4 แต้มและให้โควตา 5 ข้อความ ส่วนคำถามเดี่ยวหัก 1 แต้ม ผู้ใช้บางบทบาทอาจได้รับการยกเว้น และถ้าใช้เซสชันเดิม ระบบจะลดเครดิตที่เหลือก่อนเริ่มคำถาม

เมื่อผ่านเรื่องสิทธิ์และโควตา ระบบแปลงคำถามเป็น Embedding แล้วค้นหาเวกเตอร์ใน SurrealDB โดยใช้เฉพาะ notebook หรือ source ที่ได้รับอนุญาต การจำกัดขอบเขตนี้สำคัญ เพราะระบบไม่ควรดึงข้อมูลจากคลังอื่นที่ผู้ใช้ไม่มีสิทธิ์เห็น

จากผลค้นหา ระบบกรองชิ้นข้อความที่มีความคล้ายคลึงต่ำ ตัดข้อความซ้ำ และจำกัดจำนวนกับขนาดของบริบท ก่อนนำคำถามและข้อความที่เกี่ยวข้องมาประกอบเป็น prompt เพื่อส่งให้แบบจำลองภาษา

แบบจำลองจะสังเคราะห์คำตอบจากคำถามและบริบทที่ค้นคืนได้ จากนั้นระบบจัดรูปแบบคำตอบและหมายเลขอ้างอิง เช่น แหล่งที่ 1 หรือแหล่งที่ 2 แล้วบันทึกคำถาม คำตอบ และ citation เพื่อให้เปิดดูประวัติการสนทนาได้ ก่อนส่งคำตอบพร้อมแหล่งอ้างอิงกลับไปยังผู้ใช้

ถ้าบริการแบบจำลองทำงานล้มเหลว ระบบจะตรวจว่ามีการหักแต้มหรือเครดิตไปแล้วหรือไม่ ถ้าหักไปแล้ว ระบบบันทึกรายการคืนแต้มและคืนเครดิตตามเงื่อนไข แต่ถ้ายังไม่ได้หัก ระบบเพียงบันทึกข้อผิดพลาดและแจ้งผู้ใช้

สรุปคือ RAG ไม่ได้ให้แบบจำลองตอบจากคำถามอย่างเดียว แต่ค้นข้อมูลจากแหล่งที่ผู้ใช้มีสิทธิ์ก่อน แล้วใช้ข้อมูลนั้นประกอบคำตอบและแสดงที่มา อย่างไรก็ตาม การมีแหล่งอ้างอิงช่วยให้ตรวจสอบได้ แต่ไม่ได้รับประกันว่าคำตอบจะถูกต้องทุกกรณีครับ/ค่ะ”

### หากสไลด์แสดง Sequence Diagram ด้วย

อธิบายเสริมได้ว่า:

“ส่วน Sequence Diagram เน้นลำดับการส่งคำขอระหว่างองค์ประกอบของระบบตามเวลา เริ่มจาก Client ส่งคำถามให้ RAG API จากนั้น API ประสานการตรวจสิทธิ์และโควตา เรียกฐานข้อมูลเวกเตอร์เพื่อค้นบริบท ส่งบริบทให้บริการแบบจำลอง และรับคำตอบกลับมา ก่อนบันทึกประวัติและตอบกลับ Client ส่วน Flowchart เน้นจุดตัดสินใจ เช่น สิทธิ์ผ่านหรือไม่ แต้มพอหรือไม่ และบริการสำเร็จหรือไม่ ทั้งสองภาพจึงอธิบายระบบเดียวกันคนละมุม”

### จุดที่ควรชี้บนภาพ

1. ชี้คำถามและขอบเขตคลังที่ Client ส่งมา
2. ชี้การตรวจ JWT บัญชี บทบาท และสิทธิ์
3. ชี้เส้นทางคำถามเดี่ยว เซสชันใหม่ และเซสชันเดิม
4. ชี้การสร้าง Embedding และการค้นเวกเตอร์
5. ชี้การกรองผล การประกอบบริบท และการเรียกแบบจำลอง
6. ชี้การส่งคำตอบพร้อม citation และเส้นทางคืนแต้ม/เครดิตเมื่อผิดพลาด

### ประเด็นที่ควรจำ

- RAG คือการค้นข้อมูลที่เกี่ยวข้องก่อน แล้วให้แบบจำลองสังเคราะห์คำตอบจากข้อมูลนั้น
- ระบบต้องจำกัดการค้นตามสิทธิ์และขอบเขตที่ผู้ใช้เลือก
- Citation ทำให้ผู้ใช้ย้อนดูที่มาของคำตอบได้
- ค่าแต้มและโควตาเป็นค่าตามการตั้งค่าปัจจุบัน และอาจเปลี่ยนได้

## สไลด์ที่ 5: การสร้างแผนการเรียน AI Roadmap

**หัวข้อที่เกี่ยวข้อง:** บทที่ 3 หัวข้อ 3.5.2  
**แผนภาพที่เกี่ยวข้อง:** รูปที่ 3.12 การสร้างและขยายแผนการเรียนรู้ด้วย AI Roadmap

### ใจความสำคัญ

แผนภาพนี้แสดงการสร้างแผนจากเป้าหมายและแหล่งความรู้ที่ผู้ใช้เลือก ตรวจสิทธิ์และแต้ม ค้นบริบท สร้างผลลัพธ์แบบมีโครงสร้าง ตรวจสอบและจัดระเบียบหัวข้อเป็น 5 ระยะ บันทึกแผน และรองรับการขยายหัวข้อภายหลัง

### บทพูดสำหรับนำเสนอ

“สไลด์นี้แสดงการทำงานของ AI Roadmap ซึ่งช่วยจัดลำดับหัวข้อการเรียนรู้จากเป้าหมายที่ผู้ใช้ระบุครับ/ค่ะ

เริ่มจากผู้ใช้กรอกเป้าหมายหรือหัวข้อที่อยากเรียน ระบุจำนวนหัวข้อและภาษา เลือกแหล่งความรู้ เช่น คลังรายวิชาหรือเอกสารที่มีสิทธิ์เข้าถึง และเลือกว่าจะให้ระบบค้นข้อมูลจากเว็บหรือไม่

API ตรวจสอบรูปแบบคำขอ ตัวตน และสิทธิ์ของแหล่งความรู้ ถ้าข้อมูลไม่ถูกต้องหรือไม่มีสิทธิ์ ระบบแจ้งข้อผิดพลาดและไม่ดำเนินการต่อ ถ้าผ่าน ระบบตรวจแต้มสำหรับการสร้างแผน ถ้าแต้มไม่พอจะแจ้งผู้ใช้ แต่ถ้าเพียงพอจึงไปค้นคืนข้อมูลจากคลังในขอบเขตที่เลือก

หลังค้นข้อมูล ระบบตรวจว่ามีผลลัพธ์เดิมในแคชหรือไม่ ถ้ามี ระบบนำผลลัพธ์นั้นมาใช้เพื่อลดการประมวลผลซ้ำ ถ้าไม่มี ระบบส่งเป้าหมายและบริบทที่ค้นคืนให้แบบจำลองภาษา เพื่อให้สร้างแผนในรูปแบบ JSON

เมื่อได้รับผลลัพธ์ ระบบไม่ได้บันทึกทันที แต่ตรวจโครงสร้างและจำนวนโหนดก่อน ถ้าไม่ผ่าน ระบบคืนแต้มและแจ้งข้อผิดพลาด ถ้าผ่าน ระบบจัดข้อมูลให้เป็นมาตรฐาน กำหนดรหัสและลำดับของโหนด แล้วจัดโหนดหลักออกเป็น 5 ระยะ ได้แก่ พื้นฐาน แนวคิดหลัก ฝึกปฏิบัติ ประยุกต์ และทบทวนหรือประเมิน จากนั้นจึงสร้างเส้นเชื่อมระหว่างหัวข้อหลักและหัวข้อย่อย พร้อมผูกแหล่งอ้างอิงตามข้อมูลที่ใช้

ระบบบันทึกแผนเป็นเซสชันใน SurrealDB แล้วแสดงแผนพร้อมข้อมูลแหล่งที่มาให้ผู้ใช้ ถ้าเป็นผลลัพธ์จากแคช ระบบคืนแต้มที่เรียกเก็บไว้ตามกติกา

ผู้ใช้ยังสามารถเลือกหัวข้อในแผนเพื่อขยายเป็นหัวข้อย่อยได้ ระบบจะตรวจว่าระดับของหัวข้อและจำนวนโหนดยังไม่เกินข้อจำกัดหรือไม่ รวมทั้งตรวจแต้มก่อนค้นบริบทและสร้างหัวข้อเพิ่มเติม ถ้าผลลัพธ์ไม่ผ่านการตรวจสอบ ระบบคืนแต้มและแจ้งเหตุผล แต่ถ้าผ่าน ระบบเพิ่มโหนดและเส้นเชื่อมลงในแผน และบันทึกแผนฉบับปรับปรุง หากแผนถูกแชร์ในคอมมูนิตี้ ระบบจะปรับข้อมูลสำเนาในโพสต์ให้ตรงกับแผนที่อัปเดต

ดังนั้น Roadmap เป็นเครื่องมือช่วยวางลำดับการเรียน ไม่ได้เลือกเป้าหมายแทนผู้เรียน ผู้ใช้ยังเป็นผู้กำหนดว่าจะเรียนอะไร และควรตรวจดูเนื้อหากับแหล่งอ้างอิงก่อนนำแผนไปใช้ครับ/ค่ะ”

### จุดที่ควรชี้บนภาพ

1. ชี้ข้อมูลเป้าหมาย จำนวนหัวข้อ แหล่งความรู้ และโหมดเว็บ
2. ชี้การตรวจสิทธิ์และแต้ม
3. ชี้เส้นทางแคชเทียบกับการเรียกแบบจำลอง
4. ชี้การตรวจ JSON และการจัดเป็น 5 ระยะ
5. ชี้การบันทึกแผนและการแสดงแหล่งอ้างอิง
6. ชี้ทางเลือกขยายโหนด และเงื่อนไขระดับ/จำนวน/แต้ม

### ประเด็นที่ควรจำ

- แผนประกอบด้วยโหนดหัวข้อและเส้นเชื่อมที่แสดงลำดับหรือความสัมพันธ์
- ระบบตรวจโครงสร้างก่อนบันทึก ไม่ใช้ผลลัพธ์จากแบบจำลองโดยไม่ตรวจสอบ
- แผนจัดเป็น 5 ระยะ ตั้งแต่พื้นฐานไปจนถึงทบทวนหรือประเมิน
- การขยายแผนใช้แหล่งความรู้และขอบเขตที่บันทึกไว้กับแผน

**หัวข้อที่เกี่ยวข้อง:** บทที่ 3 หัวข้อ 3.6.2  
**แผนภาพที่เกี่ยวข้อง:** รูปที่ 3.13 การสร้างและใช้งานแบบทดสอบด้วย AI Quiz

### ใจความสำคัญ

แผนภาพนี้แสดงตั้งแต่ผู้ใช้เลือกหัวข้อ จำนวนข้อ ภาษา และแหล่งความรู้ ระบบตรวจสิทธิ์และแต้ม ค้นเนื้อหาที่เกี่ยวข้อง ให้แบบจำลองสร้างคำถาม ตรวจรูปแบบและคำตอบ บันทึกชุดแบบทดสอบ แล้วให้ผู้เรียนตอบพร้อมดูเฉลยและคำอธิบาย

### บทพูดสำหรับนำเสนอ

“สไลด์สุดท้ายนี้แสดงกระบวนการสร้างและใช้งานแบบทดสอบด้วย AI Quiz ครับ/ค่ะ

ผู้ใช้เริ่มจากระบุหัวข้อที่ต้องการทบทวน จำนวนข้อ ภาษา และแหล่งความรู้ที่ต้องการให้ระบบใช้ เช่น เอกสารหรือคลังรายวิชา จากนั้น API ตรวจสอบข้อมูลคำขอ ตัวตน และสิทธิ์ในการเข้าถึงแหล่งความรู้นั้น ถ้าคำขอไม่ถูกต้องหรือไม่มีสิทธิ์ ระบบแจ้งข้อผิดพลาดและหยุด

ถ้าผ่าน ระบบตรวจแต้มสำหรับบริการ ถ้าแต้มไม่พอจะแจ้งผู้ใช้ ถ้ามีพอจึงเรียกเก็บแต้มและค้นเนื้อหาที่เกี่ยวข้องจากแหล่งที่ผู้ใช้เลือก

ระบบจะตรวจว่ามีผลลัพธ์ในแคชหรือไม่ ถ้ามี ก็สามารถนำผลเดิมมาใช้เพื่อลดการสร้างซ้ำ ถ้าไม่มี ระบบส่งหัวข้อและบริบทที่ค้นได้ให้แบบจำลองภาษา เพื่อสร้างคำถาม ตัวเลือก คำตอบที่ถูกต้อง และคำอธิบายออกมาเป็น JSON

ก่อนบันทึก ระบบตรวจผลลัพธ์ว่ามีคำถามและตัวเลือกครบหรือไม่ แต่ละข้อมีตัวเลือก 4 รายการหรือไม่ และคำตอบที่ระบุว่าถูกต้องตรงกับตัวเลือกข้อใดข้อหนึ่งจริงหรือไม่ ถ้าผลลัพธ์ไม่ผ่าน ระบบไม่บันทึกชุดข้อสอบ และคืนแต้มที่หักไปแล้วพร้อมแจ้งข้อผิดพลาด ถ้าผ่าน ระบบบันทึกเป็น quiz session ใน SurrealDB

หลังบันทึก ระบบส่งชุดแบบทดสอบให้ผู้เรียนตอบ เมื่อผู้เรียนเลือกคำตอบ ระบบตรวจคำตอบและแสดงเฉลยพร้อมคำอธิบาย เพื่อให้ผู้เรียนเข้าใจเหตุผลและใช้ทบทวนได้ ไม่ใช่เพียงเห็นว่าถูกหรือผิด

แบบทดสอบที่สร้างขึ้นมีเป้าหมายเพื่อช่วยฝึกฝนและทบทวนความเข้าใจเบื้องต้น ไม่ควรใช้คะแนนจากแบบทดสอบ AI เพียงอย่างเดียวเป็นข้อสรุปผลสัมฤทธิ์ทางการเรียนอย่างเป็นทางการครับ/ค่ะ”

### จุดที่ควรชี้บนภาพ

1. ชี้ข้อมูลนำเข้า: หัวข้อ จำนวนข้อ ภาษา และแหล่งความรู้
2. ชี้การตรวจสิทธิ์และแต้ม
3. ชี้การค้นเนื้อหาและการใช้แคชหรือแบบจำลอง
4. ชี้การตรวจ JSON จำนวนตัวเลือก และคำตอบ
5. ชี้การบันทึก quiz session
6. ชี้ขั้นผู้เรียนตอบและระบบแสดงเฉลยพร้อมคำอธิบาย

### ประเด็นที่ควรจำ

- จำนวนข้อที่ API สำหรับแบบทดสอบจากเนื้อหารองรับคือ 1–20 ข้อ และค่าเริ่มต้นคือ 10 ข้อ
- แต่ละข้อมีตัวเลือก 4 รายการ และต้องมีคำตอบที่ถูกต้องตรงกับหนึ่งในตัวเลือก
- ถ้าผลลัพธ์ไม่ผ่านการตรวจสอบ ระบบไม่ควรบันทึกผลลัพธ์ที่ไม่สมบูรณ์
- Quiz เป็นเครื่องมือช่วยทบทวน ไม่ใช่การประเมินผลสัมฤทธิ์อย่างเป็นทางการ

## ประโยคเชื่อมระหว่างสไลด์

- **จากคอมมูนิตี้ไปยังระบบแต้ม:** “เมื่อเห็นขั้นตอนการเผยแพร่เนื้อหาแล้ว ต่อไปจะอธิบายว่าระบบใช้แต้มสนับสนุนการมีส่วนร่วมและการเรียกใช้ AI อย่างไร”
- **จากระบบแต้มไปยังการนำเข้าเอกสาร:** “บริการ AI จะทำงานได้ดีเมื่อมีแหล่งความรู้ให้ค้น ต่อไปจึงเป็นขั้นตอนเตรียมเอกสารเข้าสู่คลัง”
- **จากการนำเข้าเอกสารไปยัง RAG:** “หลังเอกสารถูกแบ่งและสร้างเวกเตอร์แล้ว ผู้ใช้สามารถถามคำถามเพื่อค้นข้อมูลจากคลังผ่าน KMITL RAG AI”
- **จาก RAG ไปยัง Roadmap:** “นอกจากถามตอบแล้ว ระบบยังใช้แหล่งความรู้ที่มีมาช่วยจัดลำดับการเรียนเป็นแผนได้”
- **จาก Roadmap ไปยัง Quiz:** “เมื่อมีเป้าหมายและหัวข้อการเรียนแล้ว ผู้เรียนสามารถใช้ AI Quiz สร้างคำถามเพื่อทบทวนความเข้าใจได้”

## ประโยคสรุปภาพรวม

“โดยภาพรวม ระบบเริ่มจากการจัดการเนื้อหาและแหล่งความรู้ ตรวจสอบตัวตนกับสิทธิ์ก่อนทำงานทุกครั้ง จากนั้นจึงใช้ข้อมูลที่อยู่ในขอบเขตที่อนุญาตเพื่อให้บริการ AI และบันทึกผลลัพธ์หรือธุรกรรมที่เกี่ยวข้อง หากขั้นตอนสำคัญไม่ผ่าน ระบบจะแจ้งข้อผิดพลาดหรือคืนแต้มตามกรณี เพื่อให้การทำงานตรวจสอบย้อนหลังได้และไม่แสดงผลสำเร็จทั้งที่ประมวลผลไม่สำเร็จ”
