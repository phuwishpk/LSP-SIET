# 3.2 การออกแบบสถาปัตยกรรมและฐานข้อมูลส่วนกลาง

ระบบ KMITL AI Workspace จัดวางบริการและโมดูลตามหน้าที่ โดยใช้ Docker Compose เชื่อมส่วนติดต่อผู้ใช้ API ฐานข้อมูล และบริการสนับสนุนเข้าด้วยกัน ผู้ใช้ส่งคำขอผ่านเว็บแอปพลิเคชัน ส่วน API ตรวจสอบตัวตนและสิทธิ์ก่อนประมวลผลและเรียกใช้คลังข้อมูลที่เกี่ยวข้อง การแยกโมดูลในซอร์สโค้ดเป็นการแยกตามขอบเขตหน้าที่ มิได้หมายความว่าทุกโมดูลเป็นไมโครเซอร์วิสที่ deploy แยกจากกัน

| องค์ประกอบ | หน้าที่ |
|---|---|
| Traefik | ทำหน้าที่ reverse proxy และกำหนดเส้นทางคำขอไปยังเว็บแอปหรือ API |
| `open_notebook_api` | ให้บริการ FastAPI และส่วนติดต่อหลัก พร้อมเชื่อมโมดูลแพลตฟอร์ม คอมมูนิตี้ และ KMITL RAG |
| `my_ai_quiz` | ให้บริการส่วนติดต่อสร้างและทำแบบทดสอบ โดยเรียก API ที่เกี่ยวข้อง |
| `ai_roadmap_generator` | ให้บริการส่วนติดต่อสร้างและใช้งานแผนการเรียน |
| MariaDB | จัดเก็บบัญชี ห้องเรียน โพสต์ ปฏิสัมพันธ์ แต้ม เอกสารกำกับ และประวัติสนทนาที่กำหนดไว้ในสคีมา |
| SurrealDB | จัดเก็บ notebook, source, source embedding และข้อมูลเซสชัน Quiz/Roadmap ของระบบหลัก |
| Redis | สนับสนุนการแคชข้อมูลและผลการประมวลผล |
| Persistent storage | จัดเก็บไฟล์ที่อัปโหลดและข้อมูลถาวรของบริการ |

## 3.2.1 แผนภาพการไหลของข้อมูลส่วนกลาง

แผนภาพการไหลของข้อมูล (Data Flow Diagram: DFD) ใช้อธิบายการรับ ส่ง ประมวลผล และจัดเก็บข้อมูล โดยเริ่มจากภาพรวมระบบแล้วแจกแจงกระบวนการหลักและคลังข้อมูลตามลำดับ

### แผนภาพบริบท DFD ระดับ 0

> [พื้นที่สำหรับแทรกแผนภาพ: รูปที่ 3.1 DFD Level 0 Context Diagram]
> **องค์ประกอบที่ต้องแสดงในแผนภาพ:**
> - ระบบ KMITL AI Workspace เป็นกระบวนการหลักหนึ่งกระบวนการ
> - ผู้ดูแลระบบ ผู้สอน และนักศึกษาเป็นหน่วยงานภายนอก พร้อมข้อมูลที่ส่งเข้าและรับกลับ
> - ผู้ให้บริการยืนยันตัวตนและผู้ให้บริการแบบจำลองภาษาเป็นระบบภายนอกเมื่อมีการเรียกใช้
> - แสดงข้อมูลบัญชี คำสั่งจัดการห้อง/เอกสาร โพสต์ คำถาม AI ผลลัพธ์ และการแจ้งเตือน

- ผู้ดูแลส่งคำสั่งจัดการบัญชี บทบาท การตั้งค่าระบบ และการตรวจสอบเนื้อหา
- ผู้สอนจัดการห้องเรียนและเอกสารประกอบการสอนตามสิทธิ์ของตน
- นักศึกษาสร้างหรืออ่านเนื้อหาคอมมูนิตี้ สืบค้นคลังความรู้ และใช้บริการ AI
- ระบบส่งผลการดำเนินงาน สถานะ และข้อมูลที่ผู้ใช้ได้รับอนุญาตกลับไปยังผู้ใช้

### DFD ระดับ 1

> [พื้นที่สำหรับแทรกแผนภาพ: รูปที่ 3.2 DFD Level 1 ระบบส่วนกลาง]
> **องค์ประกอบที่ต้องแสดงในแผนภาพ:**
> - กระบวนการ 1.0 จัดการผู้ใช้และสิทธิ์
> - กระบวนการ 2.0 จัดการคลังข้อมูลและเอกสาร
> - กระบวนการ 3.0 จัดการคอมมูนิตี้และแต้มสะสม และกระบวนการ 4.0 ประมวลผลปัญญาประดิษฐ์
> - หน่วยงานภายนอกและคลังข้อมูล D1–D4 พร้อมทิศทางการไหลของข้อมูล

- กระบวนการ 1.0 ตรวจสอบบัญชี การยืนยันตัวตน สถานะผู้ใช้ และบทบาทก่อนอนุญาตให้เรียก API
- กระบวนการ 2.0 ตรวจสอบขอบเขตคลัง บันทึกข้อมูลกำกับเอกสาร และส่งเนื้อหาเข้าสู่การสกัดและสร้างเวกเตอร์
- กระบวนการ 3.0 จัดการโพสต์ ความคิดเห็น ปฏิกิริยา การแบ่งปัน การแจ้งเตือน และธุรกรรมแต้ม
- กระบวนการ 4.0 ตรวจสิทธิ์และขอบเขตความรู้ ค้นคืนข้อมูล ประกอบบริบท เรียกแบบจำลอง และบันทึกผล

### DFD ระดับ 2 กระบวนการ 3.0: คอมมูนิตี้และแต้มสะสม

> [พื้นที่สำหรับแทรกแผนภาพ: รูปที่ 3.3 DFD Level 2 Process 3.0 Community and Points]
> **องค์ประกอบที่ต้องแสดงในแผนภาพ:**
> - รับคำขอสร้างโพสต์หรือทำปฏิสัมพันธ์ พร้อมตรวจสอบตัวตน บทบาท และสิทธิ์ของทรัพยากร
> - คัดกรองขอบเขตการมองเห็นและตรวจเงื่อนไขการบันทึกกิจกรรม
> - อ่าน/เขียนโพสต์ ปฏิสัมพันธ์ การแจ้งเตือน และข้อมูลบัญชีผู้ใช้
> - ประเมินรางวัลหรือค่าใช้จ่าย อัปเดตยอด และบันทึกรายการในสมุดบัญชีแต้ม

- ระบบตรวจสอบบทบาท ความเป็นเจ้าของ และการเป็นสมาชิกห้องก่อนดำเนินการกับเนื้อหา
- ระบบตรวจข้อกำหนดของโพสต์และป้องกันการบันทึกปฏิสัมพันธ์ซ้ำ
- เมื่อเข้าเงื่อนไข ระบบคำนวณแต้มโดยคำนึงถึงเพดานรายวันและกฎเฉพาะกิจกรรม
- การเปลี่ยนแปลงยอดแต้มถูกบันทึกเป็นธุรกรรมเพื่อใช้ตรวจสอบย้อนหลัง

### DFD ระดับ 2 กระบวนการ 4.0: การประมวลผลปัญญาประดิษฐ์

> [พื้นที่สำหรับแทรกแผนภาพ: รูปที่ 3.4 DFD Level 2 Process 4.0 AI Processing]
> **องค์ประกอบที่ต้องแสดงในแผนภาพ:**
> - รับคำถามหรือข้อกำหนดสำหรับสร้างแบบทดสอบ/แผนการเรียนและระบุขอบเขตข้อมูล
> - ตรวจสอบตัวตน สิทธิ์ โควตา และค่าใช้จ่ายแต้ม
> - ค้นคืนข้อมูลจาก SurrealDB และเรียกแบบจำลองผ่านชั้นนามธรรมของผู้ให้บริการ
> - บันทึกผลลัพธ์ แหล่งอ้างอิง ประวัติการใช้ และสถานะการคืนแต้มเมื่อเกิดความล้มเหลว

- ระบบกำหนดบริการและขอบเขต notebook/source ที่ผู้ใช้เข้าถึงได้ก่อนค้นข้อมูล
- ระบบตรวจสอบยอดหรือเครดิตและบันทึกรายการหักแต้มตามชนิดบริการ
- ข้อมูลที่ค้นคืนถูกคัดเลือกและส่งให้แบบจำลองเพื่อสังเคราะห์คำตอบหรือสร้างผลลัพธ์
- เมื่อประมวลผลไม่สำเร็จ ระบบคืนแต้ม/โควตาตามเงื่อนไขและบันทึกผลที่ตรวจสอบได้

### คลังข้อมูล D1–D4

| คลังข้อมูล | ความหมาย |
|---|---|
| **D1: Users DB** | ข้อมูลบัญชี บทบาท สถานะ และยอดแต้มใน MariaDB รวมถึงรายการผู้สอนที่ได้รับอนุญาต |
| **D2: Community DB** | ข้อมูลห้อง สมาชิก โพสต์ ความคิดเห็น ปฏิกิริยา การแบ่งปัน รายการบันทึก การแจ้งเตือน และธุรกรรมแต้มใน MariaDB |
| **D3: Storage** | พื้นที่ persistent สำหรับไฟล์แนบ เอกสารอัปโหลด และข้อมูลถาวรของบริการ แอป Roadmap แบบ standalone มีพื้นที่ PocketBase ของตนเอง |
| **D4: AI Vector DB** | SurrealDB สำหรับ notebook, source, source embedding และข้อมูลที่ใช้ค้นคืนเชิงความหมาย |

D1 และ D2 เป็นการแบ่งโดเมนข้อมูลเชิงตรรกะบน MariaDB ไม่ใช่ฐานข้อมูลแยกเครื่อง ส่วน Redis เป็นชั้นแคชเพิ่มเติม ไม่จัดเป็น D4 เนื่องจากไม่ได้ทำหน้าที่เป็นคลังเวกเตอร์หลัก

## 3.2.2 แผนภาพยูสเคสและบทบาทสิทธิ์การเข้าถึง

แผนภาพยูสเคสแสดงความสัมพันธ์ระหว่างผู้ใช้งานกับความสามารถหลักของระบบ ผู้ใช้ต้องผ่านการยืนยันตัวตน และทุกคำขอถูกตรวจสิทธิ์ฝั่ง backend อีกครั้ง การซ่อนเมนูในส่วนติดต่อเป็นเพียงการจัดประสบการณ์ใช้งาน ไม่ใช่กลไกควบคุมสิทธิ์แทน API

> [พื้นที่สำหรับแทรกแผนภาพ: รูปที่ 3.5 Use Case Diagram และบทบาทสิทธิ์]
> **องค์ประกอบที่ต้องแสดงในแผนภาพ:**
> - Actor หลัก 3 บทบาท ได้แก่ Admin, Teacher และ Student
> - กลุ่ม Use Case สำหรับการจัดการระบบ/บัญชี การจัดการห้องและคลังเอกสาร คอมมูนิตี้ และบริการ AI
> - ความสัมพันธ์ Include ระหว่างบริการ AI ที่มีค่าใช้จ่ายกับการตรวจสอบ/หักแต้ม
> - ขอบเขตระบบและกรณีปฏิเสธคำขอเมื่อบทบาท สมาชิกภาพ หรือยอดแต้มไม่ผ่านเงื่อนไข

- Admin จัดการบัญชี การกำหนดค่าระบบ และตรวจสอบการดำเนินงานตามสิทธิ์ผู้ดูแล
- Teacher จัดการห้องที่ตนเป็นเจ้าของหรือได้รับมอบหมาย และอัปโหลดเอกสารคลังรายวิชาเมื่อเป็นเจ้าของหรือผู้ช่วยสอนของห้องนั้น
- Student อ่านและเผยแพร่เนื้อหาตามระดับการมองเห็น ใช้คลังส่วนบุคคล และเรียกใช้ AI ภายใต้ยอดแต้ม/โควตา
- การเป็นสมาชิกห้องและความเป็นเจ้าของทรัพยากรเป็นเงื่อนไขเพิ่มเติมจากบทบาทหลัก

| บทบาท | ขอบเขตสิทธิ์ |
|---|---|
| **Admin** | จัดการบัญชีและสถานะผู้ใช้ ตั้งค่าระบบ ตรวจสอบรายงานและบันทึกผู้ดูแล รวมถึงใช้งานความสามารถทั่วไปตามนโยบาย |
| **Teacher** | ใช้ฟังก์ชันสำหรับบัญชีที่ยืนยันแล้ว จัดการห้องที่ตนสร้าง และจัดการเอกสารคลังรายวิชาเมื่อเป็นเจ้าของหรือได้รับบทบาท `ta` |
| **Student** | เข้าร่วมและอ่านเนื้อหาตามสมาชิกภาพ สร้างโพสต์/ปฏิสัมพันธ์ ใช้คลังส่วนบุคคล และใช้บริการ AI ภายใต้เงื่อนไขแต้ม |

ในห้องเรียน ผู้สร้างห้องเป็นผู้จัดการการตั้งค่าห้อง ขณะที่ผู้ช่วยสอนซึ่งมีสถานะ `ta` ใน `room_members` ช่วยจัดการสมาชิกและคลังเอกสารตาม endpoint ที่รองรับได้ แต่ไม่ได้เป็นเจ้าของห้องโดยอัตโนมัติ การตรวจสอบสิทธิ์ของโพสต์ประเภท `material` และการอัปโหลดเอกสารอาจใช้เงื่อนไขเฉพาะ endpoint จึงไม่ควรเหมารวมว่าทุกการจัดการเนื้อหาตรวจความเป็นเจ้าของห้องด้วยกฎเดียวกัน

## 3.2.3 การออกแบบโครงสร้างฐานข้อมูล

ระบบใช้สถาปัตยกรรมแบบ Polyglot Persistence โดย MariaDB เหมาะกับข้อมูลเชิงสัมพันธ์และธุรกรรม เช่น บัญชี สมาชิก โพสต์ และบัญชีแต้ม ส่วน SurrealDB รองรับข้อมูลเอกสาร ความสัมพันธ์แบบกราฟ และเวกเตอร์ที่ใช้ในระบบค้นคืน ข้อมูลที่เชื่อมข้ามฐานข้อมูลอาศัยรหัสอ้างอิงเชิงตรรกะ เช่น `library_notebook_id`, `notebook_id` และ `source_id` ซึ่งตรวจสอบในชั้นแอปพลิเคชัน ไม่ใช่ foreign key ที่บังคับข้ามเอนจิน

รายละเอียดความสัมพันธ์ระหว่างเอนทิตีและ ER-Diagram ฉบับสมบูรณ์ให้ศึกษาในภาคผนวก ส่วนตารางต่อไปนี้แสดงพจนานุกรมข้อมูลหลักตามสคีมาที่ใช้จริง โดยใช้ชื่อปัจจุบันของตารางและคอลัมน์

### พจนานุกรมข้อมูล MariaDB

**ตารางที่ 3.1 `users`**

| ฟิลด์ | ชนิดข้อมูล/ข้อกำหนด | คำอธิบาย |
|---|---|---|
| `id` | INT, PK, AUTO_INCREMENT | รหัสผู้ใช้ |
| `username` | VARCHAR(32), UNIQUE, NOT NULL | ชื่อบัญชี |
| `password_hash` | VARCHAR(255), NULL | รหัสผ่านที่ผ่านการแฮช |
| `display_name` | VARCHAR(128), NULL | ชื่อแสดงผล |
| `role` | ENUM(admin, student, teacher, pending), NOT NULL | บทบาทหรือสถานะรออนุมัติ |
| `email`, `google_sub` | VARCHAR(191), VARCHAR(64), UNIQUE, NULL | อีเมลและรหัสผู้ใช้จาก Google |
| `avatar_url` | TEXT, NULL | ที่อยู่รูปประจำตัว |
| `student_code` | VARCHAR(32), NULL | รหัสนักศึกษา |
| `points_balance` | INT, NOT NULL, DEFAULT 0 | ยอดแต้มปัจจุบัน |
| `library_notebook_id` | VARCHAR(128), NULL | รหัส notebook ส่วนบุคคลใน SurrealDB |
| `disabled` | TINYINT(1), NOT NULL, DEFAULT 0 | สถานะปิดใช้งานบัญชี |
