# 3.3 แผนภาพยูสเคสและการกำหนดขอบเขตบทบาท

## 3.3.1 แผนภาพยูสเคสของระบบ

รูปที่ 3.0.5 แสดงความสัมพันธ์ระหว่างผู้มีส่วนเกี่ยวข้องกับความสามารถหลักของ KMITL AI Workspace โดยจัดกลุ่มยูสเคสตามระบบย่อยห้าด้าน ได้แก่

1. **การจัดการผู้ใช้และระบบ (User & System Management):** จัดการบัญชี บทบาท สถานะผู้ใช้ การตรวจสอบการใช้งาน และการกำหนดค่าระบบ
2. **การยืนยันตัวตน (Authentication):** เข้าสู่ระบบ ออกจากระบบ ตรวจสอบสถานะบัญชี และยืนยันตัวตนด้วย Google OAuth ตามการตั้งค่าของระบบ
3. **การจัดการเนื้อหาและรายวิชา (Content & Course Management):** สร้างหรือเข้าร่วมห้องเรียน จัดการสมาชิก ค้นหาเอกสาร และจัดการคลังความรู้ส่วนบุคคลหรือของรายวิชา
4. **คอมมูนิตี้และเกมมิฟิเคชัน (Community & Gamification):** สร้างและค้นหาโพสต์ แสดงความคิดเห็น ให้รีแอ็กชัน แชร์ บันทึกโพสต์ รับแต้ม ใช้แต้ม และตรวจสอบประวัติแต้ม
5. **บริการ AI ระดับสูง (Premium AI Features):** ถาม KMITL RAG AI สร้างหรือทำแบบทดสอบ สร้างหรือขยายแผนการเรียน และเรียกดูเซสชันที่บันทึกไว้

แผนภาพสะท้อนการแยกสิทธิ์ในระดับผู้ใช้และทรัพยากร กล่าวคือ การผ่านการยืนยันตัวตนเพียงอย่างเดียวไม่ได้ทำให้ผู้ใช้เข้าถึงทุกยูสเคสได้ ระบบยังพิจารณาบทบาท ความเป็นเจ้าของข้อมูล สมาชิกภาพในห้อง และขอบเขตของแหล่งความรู้ก่อนดำเนินการ

## 3.3.2 บทบาทและสิทธิ์การเข้าถึง

ระบบกำหนดบทบาทหลักสามกลุ่มและตรวจสอบสิทธิ์ที่ backend ผ่าน middleware ร่วมกับการตรวจสอบเฉพาะ endpoint ดังนี้

| บทบาท | สิทธิ์และขอบเขตการใช้งาน |
|---|---|
| **ผู้ดูแลระบบ (System Admin)** | จัดการบัญชีและสถานะผู้ใช้ ตรวจสอบรายงานและบันทึกผู้ดูแล จัดการการตั้งค่าระบบและข้อมูลผู้ให้บริการโมเดล รวมถึงเข้าถึงความสามารถของผู้ใช้ทั่วไปตามนโยบายของระบบ |
| **ผู้สอน (Course Teacher)** | ใช้ฟังก์ชันคอมมูนิตี้และ AI ที่เปิดให้บัญชีที่ยืนยันแล้ว จัดการห้องที่ตนเป็นเจ้าของ และเพิ่มเอกสารลงคลังรายวิชาได้เมื่อเป็นเจ้าของห้องหรือได้รับการกำหนดเป็นผู้ช่วยสอนในห้องนั้น |
| **นักศึกษา (Student)** | เข้าร่วมและอ่านเนื้อหาตามสิทธิ์ของห้อง สร้างโพสต์และโต้ตอบในคอมมูนิตี้ ใช้คลังส่วนบุคคล และเรียกใช้ AI ภายใต้ยอดแต้มและข้อจำกัดของแต่ละบริการ |

การจัดการห้องเรียนใช้การควบคุมสิทธิ์ตามทรัพยากรเพิ่มเติมจากบทบาท ผู้สร้างห้องเป็นผู้จัดการการตั้งค่าห้องและการกำหนดผู้ช่วยสอน ส่วนผู้ช่วยสอนที่มีสถานะ `ta` ใน `room_members` สามารถช่วยจัดการเนื้อหาและดูรายชื่อสมาชิกได้ แต่ไม่ได้รับสิทธิ์แก้ไขการตั้งค่าห้องในฐานะเจ้าของ การอัปโหลดเอกสารเข้าสู่คลังรายวิชาตรวจสอบว่าผู้ใช้เป็นผู้จัดการห้องนั้นก่อนดำเนินการ

ข้อสังเกตเพื่อให้คำอธิบายตรงกับ implementation คือ endpoint อัปโหลดเอกสารรายวิชาตรวจสอบเจ้าของหรือผู้ช่วยสอนตามห้องอย่างชัดเจน ขณะที่ endpoint สร้างโพสต์ประเภท `material` ตรวจสอบบทบาทผู้สอนหรือผู้ดูแลและความถูกต้องของห้อง แต่ไม่ได้ใช้การตรวจสอบผู้จัดการห้องแบบเดียวกันในทุกกรณี ดังนั้นคำอธิบายเรื่องการจำกัดผู้สอนให้จัดการเฉพาะรายวิชาที่รับผิดชอบจึงใช้ได้กับการจัดการห้องและคลังเอกสารตามเส้นทางที่ตรวจสอบสิทธิ์ระดับห้อง และไม่ควรสรุปว่า endpoint ทุกชนิดใช้เงื่อนไขดังกล่าวเหมือนกัน

บัญชีที่ยังอยู่ระหว่างรอการอนุมัติหรือถูกระงับเป็นสถานะควบคุมการเข้าถึง ไม่ใช่บทบาทผู้ใช้งานเพิ่มเติมในขอบเขต Actor หลักของแผนภาพ ผู้ใช้ที่รออนุมัติถูกจำกัดให้ใช้งานเฉพาะเส้นทางที่จำเป็นต่อการตรวจสอบบัญชี

## 3.3.3 ความสัมพันธ์แบบ Include สำหรับการใช้แต้ม

ยูสเคสการเรียกใช้บริการ AI ที่มีค่าใช้จ่ายเชื่อมโยงกับยูสเคส **ใช้แต้ม (Redeem/Burn Points)** ด้วยความสัมพันธ์แบบ `<<include>>` ในแผนภาพ เนื่องจากการตรวจสอบและหักแต้มเป็นขั้นตอนที่ระบบต้องดำเนินการก่อนเริ่มงาน AI สำหรับนักศึกษา ตัวอย่างเช่น การถาม RAG แบบคิดแต้ม การสร้างแบบทดสอบ หรือการสร้างแผนการเรียน ระบบตรวจสอบยอดคงเหลือและบันทึกรายการหักแต้มก่อนเรียกผู้ให้บริการ หากยอดไม่เพียงพอจะปฏิเสธคำขอ และหากงานสร้างผลลัพธ์ล้มเหลว ระบบมีขั้นตอนคืนแต้มสำหรับรายการที่ถูกหักไปแล้ว

ผู้สอนและผู้ดูแลระบบได้รับการยกเว้นการหักแต้มตามกลไกปัจจุบัน ส่วนการใช้บริการบางรูปแบบอาจมีโควตาหรือเงื่อนไขเฉพาะเพิ่มเติมจากการคิดแต้ม เช่น การคิดเป็นหนึ่งคำถามหรือชุดข้อความในหนึ่งเซสชัน จึงต้องพิจารณาค่าใช้จ่ายตามชนิดบริการที่กำหนดในระบบ
