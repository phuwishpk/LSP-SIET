# 3.5 การออกแบบระบบผู้ช่วยอัจฉริยะด้วย KMITL RAG AI

## 3.5.1 กระบวนการนำเข้าจากเอกสารประกอบการสอน

กระบวนการนำเข้าข้อมูล (Ingestion Pipeline) เริ่มเมื่อผู้ใช้ส่งไฟล์ ระบุ URL หรือวางข้อความเข้าสู่คลังความรู้ ระบบตรวจสอบรูปแบบไฟล์ ขนาด ข้อมูลส่วนหัวของไฟล์ และความซ้ำซ้อนของเนื้อหาก่อนบันทึกไฟล์หรือข้อความ จากนั้นสร้างระเบียนกำกับใน MariaDB ตาราง `library_documents` ซึ่งระบุเจ้าของ ขอบเขตส่วนบุคคลหรือรายวิชา ชนิดเอกสาร ตำแหน่งไฟล์ สถานะการประมวลผล จำนวนชิ้นข้อความ และรหัส notebook/source ที่เกี่ยวข้อง

เนื้อหาที่ผ่านการตรวจสอบจะถูกแยกข้อความและจัดประเภทตามลักษณะข้อมูล เช่น HTML, Markdown หรือข้อความทั่วไป ก่อนแบ่งเป็นส่วนย่อย (Text Chunking) ที่เหมาะสมต่อการฝังเวกเตอร์ การตั้งค่าปริยายในระบบกำหนดขนาดชิ้นข้อความประมาณ 400 tokens และส่วนทับซ้อนระหว่างชิ้นข้อความร้อยละ 15 หรือประมาณ 60 tokens โดยสามารถปรับค่าผ่านการตั้งค่าระบบ การทับซ้อนช่วยรักษาความต่อเนื่องของบริบทที่อยู่บริเวณรอยต่อระหว่างชิ้นข้อความ และการกำหนดขนาดต่ำสุดช่วยตัดชิ้นที่สั้นจนไม่เหมาะต่อการสร้างเวกเตอร์

ระบบสร้าง embedding ให้ชิ้นข้อความด้วยโมเดลฝังเวกเตอร์ที่กำหนดไว้ แล้วจัดเก็บ source และข้อมูลชิ้นข้อความ/เวกเตอร์ใน SurrealDB ตารางเชิงเอกสารหลักประกอบด้วย `notebook`, `source` และ `source_embedding` โดย `source_embedding` เชื่อมกลับไปยัง source และเก็บลำดับ เนื้อหา และเวกเตอร์ของแต่ละชิ้น ส่วนข้อมูลสรุปหรือ insight ของเอกสารอาจจัดเก็บใน `source_insight` ข้อมูลเมตาดาต้าใน `library_documents` เชื่อมกับระเบียนเหล่านี้ด้วย `notebook_id` และ `source_id` หลังการนำเข้าระบบปรับสถานะเอกสารเป็น `ready` หรือบันทึกข้อผิดพลาดเป็น `failed` เพื่อให้ผู้ใช้ตรวจสอบและสั่งประมวลผลใหม่ได้

## 3.5.2 กระบวนการสืบค้นและสร้างคำตอบ

เมื่อได้รับคำถาม ระบบกำหนดขอบเขต notebook หรือ source ที่ผู้ใช้เลือกและได้รับอนุญาต แล้วสร้างเวกเตอร์ของคำถามเพื่อค้นชิ้นข้อความที่มีความใกล้เคียงกับคำถาม การจัดอันดับอาศัยหลักความคล้ายคลึงเชิงเวกเตอร์ โดยค่า Cosine Similarity ใช้พิจารณาทิศทางสัมพัทธ์ระหว่างเวกเตอร์คำถามกับเวกเตอร์เอกสาร ชิ้นที่สัมพันธ์สูงจะถูกนำมาประกอบเป็นบริบท ทั้งนี้การค้นในขอบเขตที่ผู้ใช้ระบุจะไม่ขยายไปยังคลังอื่นโดยอัตโนมัติเมื่อกำหนดให้ปิดการค้นสำรอง เพื่อรักษาความสอดคล้องระหว่างขอบเขตที่ผู้ใช้เลือกกับข้อมูลที่ใช้ตอบ

เส้นทางถาม KMITL RAG แบบรวดเร็วจำกัดจำนวนชิ้นข้อความที่นำมาใช้ โดยค่าปริยายค้นคืนได้ไม่เกิน 6 ชิ้น และจำกัดขนาด snippet และบริบทรวมตามค่าที่กำหนดในระบบ พร้อมตัดรายการที่ซ้ำและสร้างข้อมูลอ้างอิงกำกับแต่ละแหล่ง เส้นทางนี้ใช้การจำกัดบริบทด้วยจำนวนชิ้นและจำนวนอักขระเป็นหลัก ส่วน `ContextBuilder` ใน Open Notebook ใช้ประกอบเนื้อหา source และ insight สำหรับการสนทนากับ notebook หรือ source โดยนับโทเคนและตัดทอนเนื้อหาให้สอดคล้องกับงบประมาณโทเคนของคำขอ ทั้งสองวิธีจึงเป็นกลไกควบคุมบริบทที่ทำงานในคนละเส้นทาง

หลังการค้นคืน ระบบประกอบ prompt ซึ่งมีคำถาม ขอบเขตความรู้ ข้อความที่ค้นพบ และประวัติสนทนาตามรูปแบบการใช้งาน แล้วส่งให้โมเดลผ่านชั้นนามธรรมของผู้ให้บริการ (Model Abstraction Layer) เพื่อให้การเลือกและเรียกใช้โมเดลไม่ผูกกับผู้ให้บริการรายเดียว คำตอบที่ได้ถูกตรวจรูปแบบการอ้างอิงก่อนส่งกลับ โดยข้อความอ้างอิงในคำตอบเชื่อมโยงกับรายการ `citations` ที่ระบุชื่อแหล่งและข้อความประกอบ

ระบบมี pipeline สำหรับงานถามตอบมากกว่าหนึ่งรูปแบบ กราฟ Ask ของ Open Notebook ประกอบด้วยขั้นวางกลยุทธ์การค้นหา (Strategy) ซึ่งสร้างคำค้นและคำแนะนำ ขั้นค้นคืนและสร้างคำตอบย่อย (Provide Answer) ซึ่งสามารถกระจายการค้นตามคำค้น และขั้นสังเคราะห์ผลเป็นคำตอบสุดท้าย (Final Answer) ขณะที่เส้นทาง KMITL RAG แบบรวดเร็วเรียกค้นคลังและสร้างคำตอบจากบริบท แล้วอาจเรียกการค้นเว็บเพิ่มเติมเมื่อระดับความครอบคลุมของเอกสารหรือโหมดที่ผู้ใช้เลือกกำหนด การแยกคำอธิบายนี้สะท้อนลำดับการทำงานจริงและหลีกเลี่ยงการรวม pipeline ทั้งสองเป็นสถาปัตยกรรมตัวแทนแบบเดียว

กลไกแคชถูกใช้เพื่อลดการเรียกผู้ให้บริการซ้ำและลดเวลาตอบสนอง เส้นทางถามรวดเร็วคำนวณคีย์จากคำถาม ขอบเขต notebook/source โหมดเว็บ ภาษา และโมเดล เพื่อไม่ให้คำตอบจากบริบทหนึ่งถูกนำไปใช้ในอีกขอบเขตหนึ่ง ส่วนเส้นทาง Notebook Ask รองรับทั้ง exact match และ semantic cache โดยพิจารณาความคล้ายคลึงและการตรวจสอบความสอดคล้องของเจตนาคำถามก่อนนำคำตอบเดิมกลับมาใช้ ระบบแคชผลคำตอบและข้อมูลที่เกี่ยวข้องผ่าน Redis โดยยังคงต้องคำนึงถึงขอบเขตข้อมูลและสิทธิ์ของผู้ใช้
