# 3.2 สถาปัตยกรรมของระบบและแผนภาพการไหลของข้อมูล

## 3.2.1 สถาปัตยกรรมระบบ

ระบบ KMITL AI Workspace ใช้ Docker Compose จัดการการทำงานของบริการหลายส่วนบนเครือข่ายภายในเดียวกัน โดยมี Traefik ทำหน้าที่เป็น reverse proxy และกำหนดเส้นทางจาก URL ไปยังส่วนติดต่อหรือ API ที่เกี่ยวข้อง ผู้ใช้เข้าถึงส่วนติดต่อผ่านเว็บเบราว์เซอร์ ขณะที่การเรียกข้อมูลและส่งคำสั่งดำเนินการผ่าน REST API ซึ่งตรวจสอบตัวตนและสิทธิ์ก่อนประมวลผล

| องค์ประกอบ | หน้าที่ในสถาปัตยกรรม |
|---|---|
| Traefik | รับคำขอจากผู้ใช้และกำหนดเส้นทางไปยังเว็บแอปพลิเคชันหรือ API ตาม path |
| `open_notebook_api` | ให้บริการ FastAPI และส่วนติดต่อ Next.js หลัก รวมทั้งลงทะเบียนโมดูลแพลตฟอร์ม คอมมูนิตี้ และ KMITL RAG |
| `my_ai_quiz` | ให้บริการส่วนติดต่อแอปพลิเคชันสร้างและทำแบบทดสอบ โดยเรียก API กลางสำหรับฟังก์ชันที่เชื่อมต่อกับระบบหลัก |
| `ai_roadmap_generator` | ให้บริการส่วนติดต่อสร้างแผนการเรียนและเชื่อมต่อกับ API กลาง |
| `ai_roadmap_pocketbase` | ให้บริการ PocketBase สำหรับแอปแผนการเรียนแบบแยก และจัดเก็บข้อมูลไว้ในพื้นที่ persistent ของบริการ |
| MariaDB | จัดเก็บข้อมูลบัญชี ห้องเรียน โพสต์ การโต้ตอบ แต้ม เอกสารกำกับ และประวัติการสนทนาที่กำหนดไว้ในสคีมาเชิงสัมพันธ์ |
| SurrealDB | จัดเก็บ notebook, source, source embedding และข้อมูลเซสชันควิซหรือแผนการเรียน |
| Redis | สนับสนุนการแคชข้อมูลและผลการประมวลผลที่เกี่ยวข้องกับการเรียกใช้ AI |

การแบ่งโค้ดของระบบหลักออกเป็น `siet-platform`, `community` และ `kmitl-rag` เป็นการแบ่งตามขอบเขตหน้าที่และความรับผิดชอบ โดยแต่ละโมดูลเชื่อมต่อกับ hook ของแอปพลิเคชันหลักและใช้ API กับชั้นข้อมูลร่วมกัน การจัดวางเช่นนี้สนับสนุนการแยกพัฒนาและทดสอบโดยไม่ทำให้เกิดข้อสรุปเกินจริงว่าทุกโมดูลทำงานเป็นบริการเครือข่ายอิสระ

## 3.2.2 แผนภาพบริบท (Context Diagram: DFD ระดับ 0)

แผนภาพบริบทในรูปที่ 3.0.1 แสดงระบบเป็นกระบวนการหลักหนึ่งกระบวนการ ซึ่งรับข้อมูลจากผู้ใช้และส่งผลลัพธ์กลับผ่านส่วนติดต่อเว็บ ผู้ดูแลระบบส่งคำสั่งจัดการบัญชี สิทธิ์ การตั้งค่าระบบ และการตรวจสอบเนื้อหา ผู้สอนจัดการเนื้อหาห้องเรียนและเอกสารประกอบการสอน ส่วนนักศึกษาเข้าร่วมชุมชน สืบค้นความรู้ และใช้บริการ AI ภายใต้โควตาหรือยอดแต้มของตน ระบบยังสื่อสารกับผู้ให้บริการยืนยันตัวตนและผู้ให้บริการโมเดลภาษาตามการตั้งค่าของระบบ โดยรับผลการยืนยันหรือผลการสร้างคำตอบกลับมาประกอบการตอบสนองต่อผู้ใช้

## 3.2.3 แผนภาพการไหลของข้อมูลระดับ 1

รูปที่ 3.0.2 แจกแจงระบบออกเป็นกระบวนการหลักสี่กระบวนการ และแสดงการแลกเปลี่ยนข้อมูลกับคลังข้อมูลที่เกี่ยวข้อง ดังนี้

1. **กระบวนการ 1.0 จัดการผู้ใช้และสิทธิ์** รับข้อมูลการเข้าสู่ระบบและข้อมูลบัญชี ตรวจสอบตัวตนผ่านกลไกยืนยันตัวตนของระบบหรือ Google OAuth จากนั้นกำหนดบทบาทและสร้างข้อมูลยืนยันการเรียก API การตรวจสอบบทบาททำที่ฝั่ง backend เป็นหลัก โดยมีสถานะบัญชีและบทบาทผู้ใช้เป็นข้อมูลกำกับ
2. **กระบวนการ 2.0 จัดการคลังข้อมูลและเอกสาร** รับไฟล์ URL หรือข้อความจากผู้ใช้ ตรวจสอบขอบเขตคลังส่วนบุคคลหรือคลังรายวิชา บันทึกข้อมูลกำกับเอกสาร และส่งเนื้อหาเข้าสู่กระบวนการแยกข้อความและสร้างเวกเตอร์ ผลลัพธ์ที่ได้ถูกเชื่อมโยงกับ notebook และ source เพื่อใช้ในการค้นคืนภายหลัง
3. **กระบวนการ 3.0 จัดการคอมมูนิตี้และแต้มสะสม** รับคำสั่งสร้างและค้นหาโพสต์ คอมเมนต์ รีแอ็กชัน แชร์ และบันทึกโพสต์ ตลอดจนคำสั่งสะสมหรือใช้แต้ม ระบบตรวจสอบการมองเห็นโพสต์และความถูกต้องของธุรกรรมก่อนปรับปรุงข้อมูลและส่งผลกลับไปยังฟีด กระเป๋าแต้ม หรือการแจ้งเตือน
4. **กระบวนการ 4.0 ประมวลผลปัญญาประดิษฐ์** รับคำถามหรือข้อกำหนดสำหรับสร้างแบบทดสอบและแผนการเรียน ตรวจสอบสิทธิ์ ขอบเขตแหล่งความรู้ และค่าใช้จ่ายเป็นแต้มตามชนิดบริการ จากนั้นเรียกค้นข้อมูลจากคลังที่ได้รับอนุญาตและส่งบริบทไปยังชั้นเชื่อมต่อโมเดลภาษาก่อนบันทึกผลลัพธ์และส่งคำตอบกลับ

## 3.2.4 แผนภาพระดับ 2 ของกระบวนการ 3.0

รูปที่ 3.0.3 แสดงลำดับย่อยของคอมมูนิตี้และแต้มสะสม ได้แก่ (1) รับคำขอและตรวจสอบบทบาทหรือความเป็นเจ้าของทรัพยากร (2) คัดกรองขอบเขตการมองเห็นและเลือกโพสต์ที่ผู้ใช้มีสิทธิ์เข้าถึง (3) บันทึกโพสต์ ความคิดเห็น ปฏิกิริยา การแชร์ หรือรายการบันทึก (4) ประเมินเงื่อนไขการให้แต้มและเพดานรายวัน และ (5) ปรับยอดในบัญชีผู้ใช้พร้อมบันทึกรายการลงสมุดบัญชีธุรกรรม การออกแบบนี้ทำให้ข้อมูลการมีส่วนร่วมและข้อมูลทางการเงินเชิงแต้มสัมพันธ์กัน แต่ยังแยกวัตถุประสงค์การจัดเก็บไว้อย่างชัดเจน

## 3.2.5 แผนภาพระดับ 2 ของกระบวนการ 4.0

รูปที่ 3.0.4 แจกแจงกระบวนการปัญญาประดิษฐ์เป็นงานย่อย ได้แก่ การระบุบริการและขอบเขตข้อมูล การตรวจสอบยอดแต้มและสิทธิ์ การค้นคืนเอกสารหรือข้อมูลที่เกี่ยวข้อง การประกอบพร้อมต์และส่งคำขอผ่านชั้นนามธรรมของผู้ให้บริการโมเดล การตรวจคำตอบและจัดทำข้อมูลอ้างอิง และการบันทึกเซสชันหรือผลการใช้งาน กระบวนการ RAG ใช้เอกสารในคลังที่ผู้ใช้มีสิทธิ์เข้าถึง ส่วน AI Quiz และ AI Roadmap สร้างผลลัพธ์ตามข้อมูลนำเข้าและบริบทที่เลือก แล้วจัดเก็บเซสชันไว้สำหรับเรียกดูหรือใช้งานต่อ

ทั้งนี้ pipeline ของคำถาม KMITL RAG แบบรวดเร็วและกราฟ Ask ของ Open Notebook เป็นเส้นทางประมวลผลคนละรูปแบบ เส้นทางถามรวดเร็วค้นคืนข้อความและส่งให้โมเดลสร้างคำตอบ พร้อมอาจเรียกค้นเว็บตามเงื่อนไข ส่วนกราฟ Ask มีขั้นวางกลยุทธ์การค้นหา การสืบค้นและสร้างคำตอบย่อย และการสังเคราะห์คำตอบขั้นสุดท้าย จึงไม่ควรตีความว่าคำถาม RAG ทุกชนิดต้องผ่านลำดับตัวแทนแบบเดียวกัน

## 3.2.6 คลังข้อมูลในแผนภาพ

| คลังข้อมูล | ความหมายและขอบเขตการจัดเก็บ |
|---|---|
| **D1: Users DB** | ข้อมูลผู้ใช้ บัญชี บทบาท สถานะบัญชี และยอดแต้มในตาราง `users` รวมถึงข้อมูลผู้สอนที่ได้รับอนุญาตใน MariaDB |
| **D2: Community DB** | ข้อมูลห้อง รายวิชา โพสต์ ความคิดเห็น ปฏิกิริยา การแชร์ รายการบันทึก การแจ้งเตือน และสมุดบัญชีแต้มใน MariaDB |
| **D3: Storage** | พื้นที่ persistent สำหรับไฟล์แนบ เอกสารที่อัปโหลด และข้อมูลแอปพลิเคชันที่จัดเก็บใน volume; PocketBase มีพื้นที่ข้อมูลของบริการแยกต่างหากสำหรับแอปแผนการเรียนแบบ standalone |
| **D4: AI Vector DB** | SurrealDB สำหรับ notebook, source, source embedding และข้อมูลเชิงเอกสารหรือเซสชัน AI ที่ใช้ประกอบการค้นคืนและจัดเก็บผลลัพธ์ |

D1 และ D2 เป็นการแบ่งเชิงตรรกะตามโดเมนข้อมูล ไม่ใช่การระบุว่าเป็นเซิร์ฟเวอร์ MariaDB คนละเครื่อง ส่วน Redis เป็นบริการสนับสนุนการแคชซึ่งทำงานร่วมกับคลังข้อมูลหลัก แต่ไม่ใช่หนึ่งในคลัง D1–D4 ตามชื่อที่กำหนดในแผนภาพ
