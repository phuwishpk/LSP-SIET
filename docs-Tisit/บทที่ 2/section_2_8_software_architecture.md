# 2.8 สถาปัตยกรรมซอฟต์แวร์

## 2.8.1 สถาปัตยกรรมแบบแยกส่วนและบริการ Cloud-Native

สถาปัตยกรรมแบบแยกส่วน (Modular Architecture) แบ่งระบบออกเป็นองค์ประกอบตามหน้าที่และขอบเขตความรับผิดชอบ เพื่อลดการเชื่อมโยงที่ไม่จำเป็น ทำให้ทีมพัฒนาสามารถเปลี่ยนหรือทดสอบแต่ละส่วนได้โดยมีผลกระทบจำกัด แนวคิดด้านการตัดสินใจและการจัดการความซับซ้อนของสถาปัตยกรรมซอฟต์แวร์กล่าวถึงโดย Dehghani (2021) ส่วนแนวทาง Cloud-Native เน้นการบรรจุและบริหารบริการผ่านสภาพแวดล้อมที่ทำซ้ำได้ การกำหนดค่าแยกจากซอร์ส และการจัดการการเริ่มทำงานขององค์ประกอบที่พึ่งพากัน

ระบบจัดบริการหลายส่วนด้วย Docker Compose ภายในเครือข่ายเดียวกัน โดยมี Traefik ทำหน้าที่รับคำขอและกำหนดเส้นทางไปยังส่วนติดต่อผู้ใช้ API หลัก และแอปพลิเคชัน Quiz หรือ Roadmap โค้ดของระบบหลักแบ่งเป็นโมดูลแพลตฟอร์ม คอมมูนิตี้ และ KMITL RAG ตามหน้าที่ ทำให้สามารถพัฒนาและทดสอบเป็นส่วนได้

อย่างไรก็ตาม การแยกโมดูลใน repository ไม่ได้หมายความว่าทุกโมดูลเป็นไมโครเซอร์วิสที่ deploy และสื่อสารผ่านเครือข่ายโดยอิสระ โมดูลหลักหลายส่วนยังลงทะเบียนและทำงานร่วมกันภายใน FastAPI service เดียว ขณะที่บริการฐานข้อมูลและบางแอปพลิเคชันทำงานในคอนเทนเนอร์แยก จึงควรอธิบายสถาปัตยกรรมปัจจุบันว่าเป็นระบบแบบโมดูลาร์ที่รันบนหลายคอนเทนเนอร์ โดยมี API หลักบางส่วนทำงานร่วมกันในกระบวนการเดียว

## 2.8.2 การสื่อสารระหว่างโปรแกรมและ RESTful API

Application Programming Interface (API) กำหนดรูปแบบการแลกเปลี่ยนข้อมูลและคำสั่งระหว่างส่วนประกอบ REST เป็นแนวทางการออกแบบ API บนทรัพยากรที่ระบุได้ มีการใช้ HTTP methods ตามความหมาย และส่งข้อมูลในรูปแบบที่กำหนด การกำหนดสัญญา API อย่างชัดเจนช่วยให้ส่วนติดต่อผู้ใช้และบริการ backend พัฒนาแยกจากกันได้ ส่วนประเด็นเรื่องการควบคุมการเข้าถึง API ในสถาปัตยกรรม Cloud-Native สอดคล้องกับการศึกษาของ Rahaman และคณะ (2023) ซึ่งกล่าวถึงแนวปฏิบัติด้าน access control โดยเฉพาะ

เว็บไคลเอนต์ของแพลตฟอร์มเรียก FastAPI ผ่าน HTTP REST endpoints โดยส่งข้อมูลคำขอและข้อมูลยืนยันตัวตนตามรูปแบบ API ส่วน `open_notebook_api` เป็นจุดรวมการประมวลผลของโมดูลหลักและเชื่อมต่อกับฐานข้อมูล MariaDB, SurrealDB และ Redis ด้วย client หรือ protocol ที่เหมาะสม แอป Quiz และ Roadmap ติดต่อ API กลางสำหรับฟังก์ชันที่ใช้ร่วมกัน ส่วนการจัดเก็บข้อมูลเฉพาะของแต่ละบริการยังคงอยู่ในฐานข้อมูลของบริการนั้น

การสื่อสารภายในระบบจึงมีหลายรูปแบบ ไม่ได้ใช้ REST ระหว่างองค์ประกอบทุกคู่ การสื่อสารจาก browser ไป API เป็น HTTP/REST ขณะที่การเข้าถึงฐานข้อมูลใช้ driver ของฐานข้อมูล และการส่งงานประมวลผลเบื้องหลังอาจใช้กลไกภายในของบริการ การแยกสัญญา API ออกจากการทำงานภายในช่วยลดการเปิดเผยรายละเอียดการจัดเก็บข้อมูลแก่ส่วนติดต่อผู้ใช้
